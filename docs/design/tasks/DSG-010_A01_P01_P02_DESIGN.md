## 1. 디자인 목표

A-01의 목표는 플레이어가 공공입찰에 참여할 때 다음 다섯 가지를 혼동하지 않도록 하는 것입니다.

1. 공고의 **고정 조건**과 회사의 **현재 자격**
2. **응찰 접수**와 **낙찰 확정**
3. **접수 당시 상태**와 **마감 판정 당시 상태**
4. **낙찰**과 **사업 계약·정부 지급**
5. **사용 가능한 다음 행동**과 **이미 종료된 행동의 결과**

Stage 2 VS-01의 정상 진입 경로는 B01 공고→응찰→낙찰→사업 계약→P05 공사 화면입니다.

기획 규칙과 계산값은 DEV의 권위 snapshot을 사용하며, UI가 자체 점수 계산이나 접수 시각 판정을 수행하지 않습니다.

### P01 대표 화면 구조

| 상단 | 게임일·게임시각 / 일시정지·배속 / 회사·관할 |
|---|---|
| **공공입찰 목록** | **선택 공고 요약** |
| B01 — C01 시청 발주 | 발주기관·사업 구간 |
| B02 — C01 소재 정부 발주 | 운임 100 / 정부 사업비 800,000 |

| 공고를 선택하면 상세 정보 제공 | **[공고 상세 확인]** |
| 하단 상태 | 현재 공급 상태 / 오류 사유 / 복구 행동 |

표의 금액·기간은 승인된 기준 사례입니다. 실제 화면은 선택한 공고의 공급값을 표시합니다.

### P01 디자인 결정

- 공고 목록은 **ID와 발주기관**을 함께 표시해 서로 다른 공고를 식별하도록 합니다.
- 공고 상태는 색상뿐 아니라 `접수 중`, `접수 종료`, `결과 확정` 등의 텍스트로 구별합니다. 실제 상태명 매핑은 DEV 공급 계약 확인 후 확정합니다.
- 비노출 대상 B-X를 `신청 불가` 목록 행으로 보여주지 않습니다.
- 조회 오류를 `입찰 가능한 공고가 없습니다`로 잘못 표시하지 않습니다.
- 목록 선택은 조회·포커스이며, 그 자체로 응찰 명령을 실행하지 않습니다.

## 3. P02 공고 상세·응찰 — 정보 구조

P02는 **하나의 공고를 확인하고 응찰 결과를 추적하는 화면**입니다.

| 정보 구획 | 필수 내용 | 디자인 원칙 |
|---|---|---|
| 공고 헤더 | 공고 ID, 사업명, 발주기관, 관할, 공고 회차 | 안정 ID 표시 |
| 고정 조건 | 운임, 정부 사업비, 공사기간, 사업 구간 | 입력 불가 정보임을 명확히 표현 |
| 접수기간 | 시작·마감 게임일/시각, 현재 접수 상태 | 접수기간과 계약 효력 시각 구별 |
| 응찰 자격 | 자격별 충족 여부·거부 사유 | 부적격 원인과 다음 행동 함께 제공 |
| 사용자 행동 | 응찰 접수 요청 | DEV의 `allowed_actions`에 따라 활성화 |
| 명령 결과 | 요청 ID, 처리 상태, 접수 효력 시각 | 명령 접수와 유효 응찰 접수 구별 |
| 입찰 결과 | 낙찰/탈락, 점수·비교 근거·동점 우선순위 | 판정 당시 고정 기록 사용 |
| 사업 계약 | 유효 계약 ID·시각, 정부 지급 결과 | 계약과 지급의 의미 분리 |
| 후속 이동 | 허용된 공사 화면으로 이동 | P05 공급 조건에 따름 |

### P02 정보의 읽기 순서

**① 어떤 공고인가 → ② 조건이 무엇인가 → ③ 지금 응찰 가능한가 → ④ 요청이 처리됐는가 → ⑤ 판정 결과는 무엇인가 → ⑥ 계약과 정부 지급이 유효한가 → ⑦ 다음에 무엇을 할 수 있는가**

사용자가 입찰에 참여하는 과정에서 가장 먼저 확인해야 할 것은 응찰 자격과 접수 마감입니다. 점수나 계약 결과는 실제 판정이 발생한 뒤의 정보로 구분합니다.

## 4. P02 상태 전이·표현 매트릭스

아래 상태명은 **UI 설계용 의미 구분**이며 Godot enum을 확정하는 것이 아닙니다.

| UI 상태 | 사용자에게 표시할 핵심 문구 | 행동·제한 |
|---|---|---|
| 공고 조회 가능 | `공고 조건을 확인할 수 있습니다.` | 상세 확인 |
| 접수기간 전 | `아직 응찰 접수기간이 아닙니다.` | 접수 요청 비활성 또는 실제 거부 사유 제공 |
| 접수 가능·자격 충족 | `현재 응찰할 수 있습니다.` | 응찰 접수 요청 가능 |
| 자격 미충족 | `응찰할 수 없습니다: [사유]` | 현재 허용된 확인·복구 행동 안내 |
| 명령 처리 중 | `응찰 요청을 처리하고 있습니다.` | 실제 pending이 공급된 경우에만 표시 |
| 유효 접수 완료 | `응찰이 접수됐습니다. 마감 판정을 기다립니다.` | 접수 게임분·대상 회차 표기 |
| 접수 마감 | `이 공고의 응찰 접수가 종료됐습니다.` | 동일 회차 신규 응찰 차단 |
| 낙찰 확정 | `낙찰됐습니다.` | 판정 당시 점수·근거 표시 |
| 탈락 확정 | `입찰에서 탈락했습니다: [근거]` | 동일 회차 재응찰 가능하다고 안내하지 않음 |
| 계약 유효 | `사업 계약이 유효합니다.` | 계약 ID·효력 게임분 |
| 정부 지급 반영 | `정부 사업비 지급이 반영됐습니다.` | 실제 지급·제한금 출처 분리 |
| 후속 공사 이동 가능 | `공사 단계로 이동할 수 있습니다.` | 실제 공급된 이동 행동 제공 |

### 상태 설계의 핵심 제약

**명령의 `accepted=true`가 곧 유효한 입찰 접수를 뜻한다고 단정하지 않습니다.** DEV가 명령 수락과 유효 접수 상태를 어떻게 표현하는지 공급한 결과에 따릅니다.

낙찰, 계약 및 정부 지급이 같은 게임분에 완료되더라도 사용자가 이해할 수 있도록 서로 다른 사실로 표시합니다. 다만 모델에 존재하지 않는 지연 단계나 애니메이션용 대기 상태를 추가하지 않습니다.

## 5. 응찰·계약 사용자 조작 흐름

| 단계 | 사용자 행동 | 화면 결과 및 검증 기준 |
|---|---|---|
| 1 | P01에서 B01 선택 | B01의 발주기관·고정 조건을 P02에 표시 |
| 2 | 자격·접수기간 확인 | 현재 시각과 권위 자격·허용 행동 표시 |
| 3 | 응찰 버튼 선택 | command_id를 갖는 단일 명령 실행 |
| 4 | 명령 응답 수신 | 실제 접수 여부·접수 게임분·사유 확인 |
| 5 | 게임시간 진행 | 접수 상태와 마감 판정 상태를 구분 |
| 6 | 마감 결과 확인 | 판정 당시 점수·경쟁자·동점 근거 표시 |
| 7 | 사업 계약·지급 확인 | 유효 계약·정부금 반영 여부 별도 확인 |
| 8 | 후속 행동 선택 | 허용된 경우 P05 공사 화면 진입 |

### 중복 클릭·오래된 결과 처리

- 유효 접수가 확인되기 전에는 완료 문구를 표시하지 않습니다.
- 동일 명령 재수신으로 동일한 입찰이 두 번 접수된 것처럼 표시하지 않습니다.
- 오래된 응찰 결과가 새로운 회차의 `allowed_actions`를 덮지 않습니다.
- 현재 재무와 과거 낙찰 판정에 사용된 자금·점수를 섞지 않습니다.
- 변경된 조건으로 자동 재접수하지 않고, 실제 사유에 따라 사용자가 다시 확인하도록 합니다.

## 6. 접수기간·판정 시각의 디자인 적용

Planning이 확인한 게임시각 경계를 UI 설계에 반영합니다.

| 게임분 | 디자인 표현 기대 |
|---|---|
| T359 | 접수 시작 전 |
| T360 | 접수 시작 |
| T1439 | 접수기간 내 |
| T1440 | 야간이어도 접수기간 내 |
| T1799 | 마지막 유효 접수 게임분 |
| T1800 | 신규 접수 마감 / 기존 응찰 판정 |
| T1801 | 마감 후 |

야간 응찰을 `다음 업무 시작 대기`로 표현하지 않습니다. 이는 공고기간 안의 야간 응찰에 별도 접수 제한이 없다는 기획팀의 확인에 따른 것입니다.

**T1800에서 기존 응찰에 대한 낙찰 판정이 발생할 수 있다는 사실과, T1800의 새로운 응찰 요청이 거부된다는 사실은 동시에 성립합니다.** 화면 상태는 이 두 사건을 구별해야 합니다.

## 7. 낙찰 점수 정보 구조

### 정상 판정 예시

| 항목 | 플레이어 | 경쟁자 |
|---|---:|---:|
| 공개 표시점수 | 86 | 80 |
| 내부 정수 비교값 | 860 | 800 |
| 결과 | 낙찰 | 탈락 |

점수는 사용자가 이해할 수 있는 공개 표시값을 중심으로 제공하고, 실제 모델의 비교값·근거는 결과 설명에 연결합니다.

### 자금 변동 반례

접수 당시 F가 1,000,000이었더라도 마감 판정 시 F가 800,000이면 재무점수와 비교 결과가 달라질 수 있습니다.

이 경우 사용자에게는 다음 정보가 명확히 구분되어야 합니다.

- 접수 당시 자금·자격: **과거 접수 이력**
- 마감 당시 F 및 재무점수: **실제 판정 기준**
- 플레이어 80 대 경쟁자 80: **동점**
- 경쟁자 우선: **사전 공개된 동점 기준에 따른 탈락**

UI는 `접수 당시에는 86점이었으므로 낙찰돼야 한다`는 잘못된 메시지를 제공하지 않습니다.

## 8. 오류 및 복구 메시지 기준

| 오류 상황 | 사용자 안내 원칙 |
|---|---|
| 공고 조회 실패 | 오류·재조회 가능 행동 구분 |
| 공고 없음 | 정상 빈 목록으로 표시 |
| 관할 불일치 | 원인 설명. 외부 관할 공고는 애초 목록 비노출 |
| 자격 미충족 | 실패한 실제 자격 항목과 현재 허용 행동 |
| 접수기간 전·후 | 시작 전 또는 마감 여부 명확히 표시 |
| 이미 접수된 명령 | 기존 요청 결과 확인, 새 접수 성공처럼 표시 금지 |
| 동일 종료 회차 재응찰 | 회차 종료·재응찰 불가 사유 표시 |
| 변경된 조건 | 현재 조건 재확인 안내, 자동 접수 금지 |
| 오래된 명령 결과 | 당시 결과와 현재 상태를 분리 |
| 정부 지급 미완료 | 계약과 지급을 동일 상태로 표시하지 않음 |

색상은 보조 수단이며, 정상·경고·거부·잠금·선택 상태를 텍스트와 구조로 식별할 수 있어야 합니다.

## 14. P02 저충실도 배치·조작 상세

```text
[기존 HUD: 회사 C01 | 게임일/게임시각 | 정지·1/2/4배속]
[목록으로] 공공입찰 > B01 / 회차 / C01 시청
┌ 고정 조건(읽기 전용) ──────────┬ 현재 응찰 가능 여부 ─────┐
│ P-A 사업 구간·순서역           │ 관할/중복/공기 자격 + 사유│
│ 운임 100 / 정부금 800,000      │ 접수 시작·마감 / 현재상태 │
│ 공기 2,880게임분(계약 효력부터)│ [응찰 접수 요청]          │
└──────────────────────────────┴─────────────────────────┘
[요청 이력] command ID / 요청분 / 실제 접수분 / 처리 사유
[마감 판정 당시] 판정분 / 자격·F·점수·경쟁자·동점순위
[사업 계약] ID·상태·효력분   [정부 지급] 거래·금액·효력분
[공사 화면 확인: 현재 허용 시] / 차단 사유
[상태·오류·재조회]                    [기존 S01 복귀]
```

이는 상대적 정보 위계이며 고정 해상도나 픽셀 규격이 아니다. 좁은 화면은 조건→자격→요청→판정→계약/지급 순서로 세로 배치하고 스크롤로 접근한다. 긴 기관명/사유는 줄바꿈하며 ID·마감·핵심 행동을 가리지 않는다.

P01 최초 진입은 헤더→목록→선택 요약→상세→상태/복귀 순서로 읽는다. 방향키로 행을 선택하고 Enter/상세 버튼으로 P02를 연다. P01 선택/재조회는 응찰하지 않는다. P02 Tab 순서는 목록복귀→공급된 조작/응찰→요청이력·결과 접근→허용된 P05→복귀다. Enter/Space는 포커스된 버튼만 실행한다. 목록복귀 시 같은 공고 ID/스크롤/포커스를 가능한 범위에서 복구한다. 대상이 사라지면 선택 해제와 이유를 알리고 다른 행을 자동 실행하지 않는다.

비활성 버튼 곁에 사유를 항상 표시하고 색상 외 상태 텍스트·포커스 테두리를 둔다. 조회 갱신은 현재 포커스를 빼앗지 않는다. 응찰 선택 시 화면에 보이는 공고/회차/계획/조건을 한 명령과 연결한다. 별도 모달·새 계약 조건 입력·낙찰 후 확인 명령을 추가하지 않는다. pending이 실제 있는 경우에만 해당 요청의 연속 클릭을 억제하며 새 응찰이나 자동 재전송을 만들지 않는다. 서버 중복 방지와 실제 허용 판정은 DEV 책임이다.

snapshot_revision 증가 자체는 조건 변경 거부 사유가 아니다. 실제 대상/계획/회차/조건 차이를 공급받는다. 최신 현재 패널, 접수 이력, 마감 판정 사본, 계약/지급 사건은 각각 소속 ID·revision·게임분을 갖는다. UI 수신 벽시각은 게임시각이나 효력 판정의 입력이 아니다.

공개 점수와 동점 우선순위는 응찰 전에도 공고의 평가 기준으로 읽을 수 있어야 한다. 실제 결과점수는 판정 후 표시하고 접수 전 예상치를 확정 결과로 표시하지 않는다. 마감 F 변동은 판정 사본으로만 설명한다. UI는 clamp/정수 비교/표시 변환을 재계산하지 않는다.

계약·정부금 효력은 실제 공급된 분과 CONTRACT 단계에 따르며 같은 T 후순위 운임을 선사용하지 않는다. 정상 B01 계약 직후 기대 C1,800,000/R800,000/F1,000,000/K0/B0은 정적 fixture다. B01의 K0을 미래 정부금 초과 공사 정책으로 일반화하지 않는다. 상세 재무 설명은 UI-DC-05/F-02가 적용되는 화면 통합에서 검수한다.
