## 2. PLN-R02 — 신규 탑승 제한·동일 T 정산 및 재개 표현

**화면 목적:** 비용 미지급의 자동 정산, 승객 도착, 신규 탑승 가능 여부, 신규 사업 계약 가능 여부를 **서로 다른 의미**로 전달한다.

**결정 문구:**

> 게임 시각 T: 도착 완료 운임 인식 → 같은 T에서 미지급 B 우선 정산 → 같은 T의 영업/다음 서비스 구간 비용 및 기타 조건 확인 → 신규 탑승 허용 여부 판정.

UI-DC-06의 구 표현 `다음 T 탑승 재개`는 한 틱 추가 지연으로 오해될 수 있으므로 **사용하지 않는다**. UI는 임의 계산 없이 DEV 공급 `snapshot_revision`, `simulation_minute`, `observation_phase`, `allowed_actions/reason_codes`의 안정된 완료 상태를 표시한다.

| 게임 상태 / 판정 조건 | P06/HUD 표시 | 다음 사업 화면과의 관계 | 정적 검수 항목 |
|---|---|---|---|
| B>0, 기존 이동 중 승객 있음 | `미지급금 발생`, `신규 탑승 제한`, `이동 중 N명`; 도착 연출 유지 | **미지급 자체**는 새 사업 계약 금지 사유 아님 | B3·현금 지출0 경계; 허용 행동 공급값 사용 |
| T에 완료 운임으로 B=0, 영업 중·다음 비용 충당 가능 | `미지급 정산 완료`와 `신규 탑승 가능`을 별개 표시 | 신규 계약 가능 여부는 자격·시각·K/A 검사를 **별도** 표시 | 같은 T의 정산 후 승차 판정 |
| T에 B=0이나 영업 외 | `미지급 정산 완료` + `영업시간 외: 신규 탑승 불가` | 새 계약 불가라고 자동 확장 금지 | **2일 00:09**에 B0이더라도 06~24 영업 외 |
| B=0이나 다음 구간 비용 부족 / 그 밖의 사유 | `미지급 없음` + 실제 `신규 탑승 제한 사유` | 계약 가능성은 별도 | B=0 단독으로 자동 재개 표시 금지 |
| 미수신/미확정 또는 서로 다른 revision | `현재 탑승 상태 확인 중`, 최신 상태 다시 확인 유도 | 오래된 허용 상태 재사용 금지 | `자료 없음`과 허용값 `false` 구분 |

**승인된 경계 사례:** 1일 23:59 승객8 탑승·10분 이동 → 2일 00:09 완료8/운임800. 기존 B500 즉시 상환→B0, 다른 제약 없을 때 자유현금 순증300; 기존 승객 도착만의 추가 운영비0(CLOSE-01), 전일 보고 불변. 그러나 **00:09는 비영업 시간**이므로 탑승 버튼은 영업시간 사유로 비활성. 이 수치는 *화면 테스트용 정적 기대값*이며 실제 플레이 PASS가 아님.

**구현 경계:** UI가 미지급 정산이나 승차 가능 여부를 계산하지 않는다. 실제 허용 행동과 이유는 Development에서 동일 T의 시뮬레이션 완료 스냅샷으로 제공해야 한다.

## 3. PLN-R05 — 행정관할과 시각 지도 경계 분리

**화면 목적:** 4구·8동·후보역12곳과 유효 노선을 시각적으로 탐색하되, 화면상의 구획/클릭이 승인된 행정 관할 규칙을 대신하지 않도록 한다.

**DSG 자체 결정:** 승인 DATA v1.3의 역 좌표가 4열×3행이므로 *그 좌표에 대응하는 추상 4×3 격자*를 기초 지도로 사용한다. 이것은 **프로토타입용 디자인 구획**이며 지적도/법정 행정 경계 데이터가 아니다.

| 시안 구획 | 셀/역 배치 | 관할 표기(승인된 소속 ID 활용) | 표현 결정 |
|---|---|---|---|
| 상단 왼쪽 2셀 | S01·S02 | G01 / D01·D02 | 구 경계는 굵은 점선 + 텍스트 |
| 상단 오른쪽 2셀 | S03·S04 | G02 / D03·D04 | 인접 구 구분 라벨 |
| 중단·하단 왼쪽 2열 | S05·S06 / S09·S10 | G03 / D05·D06 | 같은 동의 다중 후보역은 역별 고유 ID로 분리 |
| 중단·하단 오른쪽 2열 | S07·S08 / S11·S12 | G04 / D07·D08 | 같은 동의 다중 후보역은 역별 고유 ID로 분리 |

위 면적·경계는 화면 설계를 위한 **선택적 도형 배치 제안**이다. 지리적 포함으로 부모/관할·사업 유효성을 판단하지 않으며 데이터에 없는 확정 폴리곤을 창작하지 않는다. 상세 패널에 `역 ID / 동 ID / 구 ID / 소속 시`를 표시한다. 월드의 관할·역 이동 가능 여부는 DEV/Planning의 실제 고유 ID 및 간선 판정이 권위다.

**DD-01:** 행정·수요·사업 중 하나만 강하게 강조하고 나머지는 낮은 우선순위로 표현한다. 색상만으로 상태 구별하지 않고 경계 선 종류/굵기·문구·범례를 함께 사용한다.

**DD-04:** 지도 마커 클릭과 순서 목록에서 선택/해제·위/아래 정렬·제거·되돌리기 및 제출 전 최종 순서를 **동등하게** 제공한다. 드래그로만 조작하도록 만들지 않는다. 40×40px 목표 클릭 영역은 **미승인 시안 가설**이며 작은/겹침 마커는 목록으로 동일 동작을 지원한다.

| 노선 편집 상태 | 표현 / 가능한 다음 동작 | 정상·오류 테스트 |
|---|---|---|
| 후보 12곳 · 미선택 | 후보/선택/확정 마커 구별; 역 목록 제시 | 역 ID·소속 표시 |
| 고유 6역 / 8역, 유효 연결 | 순서형 노선 미리보기, 제출 전 확인 가능 | DATA의 유효 경로 fixture (6/8) |
| 5역 / 9역 | 선택 개수·허용 범위 명시, 제출 불가 사유 | 최소/최대 경계 |
| 역 중복·재방문 | 해당 역 목록 행과 지도 마커 동시 강조, 제거·수정 안내 | 중복 역 fixture |
| 역 사이 단절 | 문제 연결 구간 강조, 순서 변경·제거 안내 | 미연결 간선 fixture |
| 시 관할 외 역 | 소속 관할/불가 이유 제시, 제출 차단 | 별도 오류 fixture (MVP 12후보는 모두 소속 시) |
| 심사 중 잠금 | 계획 revision·잠금 사유 표시, 편집 비활성 | 재제출 조건을 UI가 창작하지 않음 |

행정 부모·좌표·간선·판정의 실제 공급은 DEV/Planning 소관이며, 상세 지도·역 에셋의 시각 규격 확정 전에 지도/목록 동등 조작 및 밀집 검수 필요.

## 5. PLN-R04 — 예측·도착시각·생성/조회 시각 표시 기준

**공통 기존 계약(초안)으로 소비 가능한 것:** `rules_version/data_version`, `snapshot_revision`, `simulation_minute/day_id`, `observation_phase`, `entity_id/plan_revision`, `period_start/end`, `available/value`. UI는 같은 revision·관측 단계의 안정값만 한 화면에서 비교하며, 이전 계산 결과를 현재 계획 값처럼 설명하지 않는다.

| 상황 | 화면 표현 결정 | 수용한 공급 의미(§9, 구체 타입은 후속 DEV 계약) |

### 9.3 명령 결과·오래된 화면의 UX 결정

- 결과 카드는 `command_id + effective_at + decision_phase + decision_snapshot_revision + result_revision + reason`에 연결한다. `접수/대기`, `효력 당시 수락/거부`, `현재 상태/새 입력 가능`을 별도 표시한다.
- 늦은 거부 응답은 해당 명령 기록에만 추가하고 최신 snapshot의 허용 버튼을 덮지 않는다. FX-R01-A는 `당시 자기부담금 1,000 부족으로 계약 거부`와 `현재 향후 약정 여력 80,000`을 병기하며 자동 재시도/성공 소급 변경을 하지 않는다.
- expected_snapshot_revision은 입력 근거다. 시계 진행으로 봉투 revision만 바뀌었다고 일괄 거부하지 않는다. 계획revision·회차·계약조건 등 확인한 의미가 달라진 STATE_CHANGED는 갱신·재확인 안내, 실제 부족/마감/관할오류는 해당 사유로 안내한다. UI가 변경 금액/계획을 대신 확정하지 않는다.
- 동일 command_id 재수신은 기존 결과 표시만 갱신한다. 새 시도는 현재 상태를 확인한 사용자의 명시적 새 입력이며, 과거 거부를 재클릭/새로고침으로 성공 처리하지 않는다. 구체 enum·명령 타입은 DEV 소관이다.
- 정적 경계 대조: 대기→효력수락/거부, 거부 후 현재허용, STATE_CHANGED 후 재확인, 동일 ID 중복, 지연/역순 결과를 위 규칙에 연결했다. 실제 입력·네트워크·경제효과 검증은 NOT_RUN.

### 9.4 예측·cohort·시간의 확정 소비 방식

- 기존 봉투 재사용: snapshot_revision은 현재 묶음 일관성, simulation_minute/day_id는 그 snapshot 생성 게임시각, plan_revision·period_start/end·observation_phase·available/value는 계획/기간/현재완결·과거/없음·0 구분이다. 같은 뜻의 현재 생성시각 필드를 추가 요구하지 않는다.
- 추가 공급 수용: prediction_input_revision, NOT_CALCULATED/CALCULATING/READY/FAILED, prediction_reason, 결과 소속 입력revision·입력기준 게임시각·결과생성 게임시각·현재입력 유효성. READY이며 현재입력 일치/유효한 값만 현재 예측으로 소비한다. 이전값은 `이전 결과 / 입력 버전 / 기간` 별도 비교용이며 제출판정에 사용하지 않는다.
- 미계산은 `자료 없음: 미계산`, 계산중은 `예상 결과 갱신 중`, 실패는 `예상 계산 실패: 사유`, READY/available=true/value=0은 `0`으로 표시한다. 동기 계산은 READY/FAILED로 직접 종료 가능하며 로딩 연출을 위해 대기시간을 만들지 않는다.
- ETA는 노선/출발역/도착역/탑승게임분/예정도착게임분/운임조건이 같은 통행의 count 집계다. `이동 중 8명 / 도착 예정 12:05 6명, 12:06 2명`처럼 표시한다. 12:05 실제완료6 이후 이동중2가 공급되며 cohort 합계와 in_transit_count 일치를 검수한다. 일정 미제공은 `도착 예정 자료 없음: 사유`; 8명 전체를 한 시각 도착으로 합치지 않는다.
- 예정은 현재 모델 일정이며 실제 완료 effective_at과 구별한다. 최신 revision을 반영하되 정시보장·오차 수치·개별 시민 객체/애니메이션 요구를 추가하지 않는다. UI 로컬 수신/표시 시각은 필요시 진단용이고 예측 생성시각/event T/보고일을 덮거나 게임시간·난수·경제효과에 역사용하지 않는다.
