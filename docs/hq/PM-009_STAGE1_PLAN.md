## 2. Stage 1의 목적과 경계

**Stage 1 — 실행 가능한 최소 게임 기반과 행정·시각·자금 규칙의 검증 가능한 통합.**

- 장기 목표: DEV의 **VS-01(공공입찰 B01→계약·시공·시험→운행·보고→다음 사업)**, 그 후 **VS-02(자체 제안 경로)**로 확장. 두 개는 독립 VP-02/VP-01 인수 의무를 유지.
- **Stage 1은 VS-01 완주가 아니다.** Stage 1에서 확보할 것은 Godot로 시작되는 최소 화면/동작과 승인 데이터의 읽기, 안정적인 행정·역 선택/검사, 정수 게임 시각·재무 원장 검산 기반이다.
- **구현 범위:** W01 전부의 최소 실행/검사 기반, W02의 승인된 시간·장부 규칙/정적 재현, W03의 행정·후보·노선 유효성 및 승인된 최소 수요 예측 순수 계산, 제한된 S01/P03 사용자 확인용 화면. 이때 각 작업의 기능 ID·AC는 **최종 MVP AC 합격이 아니라 Stage 1의 해당 부분 증거**만 수집.
- **디자인 범위:** 공통 셸·후보역·노선 선택의 저충실도 화면/상태 표현과 지도·목록 동등 조작 사양; 필요한 최소 시안·에셋만 제안. 제품 전체의 아트 시스템·최종 에셋 제작은 제외.
- **기획 범위:** 기존 승인 데이터/관할·노선/장부/사건 T 해석에 관한 직접 질문에 한정한 확인, 새로운 게임 정책 창설 불가.

### 4.1 Stage 종료와 불합격 기준

- **Stage 통합 종료 필수:** S1-AC01~09 증거, Dev/Design의 해당 부분 자체 검증, 필요한 L2 수용 기록, HQ 잔여 결함/차단 보고, Owner의 Stage 1 결과 수용.

## 6. 영향 등급과 승인·Git 경계

- S1-DEV-01 테스트 기반은 원칙적으로 L1(부서 내부, 외부 계약 미영향). S1-DEV-03과 S1-DSG-01의 데이터/UI 계약은 **L2**. W02의 공통 시간/경제원장은 **잠재 L3 위험**으로 HQ 통합 추적하되, **이미 승인된 규칙을 충실히 구현하는 행위 자체를 기획 규칙 변경으로 간주하지 않는다**. 승인 규칙 변경·심각한 부서 충돌 시에만 L3 상정.
- INF는 세션 연속성/후임 안전 전환 소관이며, Stage 1 전문 기술·디자인·게임 규칙/일정 결정을 대행하지 않음.
- 개별 실행 작업에는 `담당/티켓 ID/연결 Issue/기준 SHA/수정 허용 경로·브랜치/AC/선행/테스트/Commit·Push·PR 허용 여부/권한 종료 조건/금지 사항`을 작성하여 **Owner 승인**을 받아야 한다.
- PR 생성·원격 CI `policy`/`department-policy` 성공은 Owner의 `main` 병합·실제 제품 인수·릴리스 승인과 별개다. 부서별 작업은 각 부서의 승인 폴더에서만.
- 본 `PM-009`의 Commit/Push/PR 승인만으로 DEV/DSG/PLN 티켓의 쓰기 권한을 생성하지 않는다.
