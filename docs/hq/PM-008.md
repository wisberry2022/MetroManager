## 1. 승인된 Gate 3 운영 8개 원칙

1. 기존 **기획 선행 → 전 부서 검토 → HQ 통합**의 강제 직렬 흐름에서 벗어나, 기획·디자인·개발이 **동일한 승인 Gate 2 기준선**에서 병렬로 분석을 시작한다.
2. 일반적인 검토 결과는 별도 장문 Markdown 검토서 대신 **GitHub PR 리뷰·댓글**로 제출한다.
3. **GitHub Issues**를 작업·RFC·버그·차단사항의 추적 수단으로 사용한다.
4. 변경 영향도에 따라 **L1/L2/L3** 검토를 적용한다.
5. HQ는 **Stage, 부서 간 의존성, 위험, 승인 및 통합 인수**에 집중하며 전문 설계를 대행하지 않는다.
6. Owner는 **승인된 개별 티켓의 범위와 기간**을 명시해 Commit/Push/PR 생성·수정 권한을 위임할 수 있다.
7. **main 병합, 주요 기획·MVP 범위 변경, 릴리스**는 Owner 최종 승인을 그대로 유지한다.
8. **첫 Stage에서 시범 운영**한 뒤 실제 전달 비용·검증 누락·품질·병목을 평가하여 필요한 정책만 개선한다.

A안 승인: 초기에는 기존 부서별 Markdown 티켓·`policy`·`department-policy`를 모두 유지한다. GitHub Issue를 추가 관리 원장으로 도입하고, Issue-only 티켓 검증으로의 변경은 아직 승인하거나 시행하지 않는다.

## 2. 목표와 단계 운영

- Gate 3-0: Planning, Design, Development가 **동일한 Gate 2 승인 문서와 SHA**로 각 전문 영역의 작업 분해·선행조건·검증 기준을 병렬 제출한다. **기획팀의 전체 결과를 개발/디자인 착수 선행 조건으로 삼지 않는다.**
- Gate 3-1: HQ가 교차 의존성을 통합하고, 첫 **Stage / 플레이 가능한 Vertical Slice**의 우선 목표·차단 조건·검증 증거와 실행 티켓을 Owner에게 제안한다.
- Gate 3-2: Owner가 실행 범위·티켓별 권한을 승인한 뒤 부서가 독립 작업을 수행하고 필요 부서만 교차 검토한다.
- 반복 점검: **Stage → Vertical Slice → Task → Weekly Priority**를 적용한다. 주차는 고정 납기가 아니라 결과·장애·다음 우선순위 점검 단위다.
- 인간 맨먼스나 디자인 8시간/일 추정으로 AI 실행 날짜를 기계적으로 약속하지 않는다. 그러나 테스트·통합·Owner 검수·반복 실패·도구 사용량 등 실제 비용과 지연 원인은 추적한다.
- **품질 상한:** 승인된 기능·AC를 충분히 충족하면 해당 Stage의 목표로 삼는다. 무제한 폴리싱·미승인 신규 기능·과도한 추상화는 별도 RFC/Owner 결정이 필요하다.

본 운영 규정의 예시 Stage(행정/역→시간/원장→사업 취득/시공→운영/VP)는 **최종 WBS가 아니다**. 실제 의존성·우선 순서는 각 부서 제안과 HQ 통합 후 확정한다.

## 4. GitHub Issue·PR·기존 티켓의 공존

### 4.1 Issues: 작업 및 블로커 추적 원장

각 Issue에 `작업 ID / 담당 / Gate2 근거 문서·SHA / 목표·비범위 / 선행·관련 Issue / AC / 권한 범위 / 상태 / 연결 PR / 차단요인`을 기재한다. RFC는 질문·대안·영향도·답변 책임을 명시한다.

**현재 필수 Markdown 티켓:** CI는 `docs/<부서>/tasks/<TASK-ID>_*.md`를 요구한다. 따라서 Issue를 만들더라도 해당 부서의 공식 최소 Markdown 티켓을 유지하고 서로의 링크·상태를 대조한다. Issue 생성 자체는 Git Commit/Push/PR 권한을 부여하지 않는다.

### 4.2 Pull Request: 경량 검토 기록

일반 검토는 PR의 리뷰/댓글에 `검토 부서 / 대상 PR head SHA / 영향 기능·파일 / 판정(ACCEPT·CHANGES_REQUESTED·BLOCKED) / 핵심 이유·수정·NOT_RUN`을 간결하게 기록한다. 중요한 정책 변경은 댓글만으로 승인 완료 처리하지 않고 승인 문서·DEC/RFC에 반영한다.

한 GitHub 계정을 여러 에이전트가 공유하므로 댓글의 부서 표기는 협업 식별 정보이지 독립 신원 인증이 아니다. 기존 `policy`, `department-policy`, Owner Merge 승인은 절대 생략하지 않는다.

## 5. L1/L2/L3 변경 영향 검토

| 등급 | 적용 범위 | 요구되는 검토 |
|---|---|---|
| **L1** | 기존 승인 명세 내 부서 내부 변경, 교차 계약 영향 없음 | 담당부서 자체 검증, 테스트 증거, PR/CI |
| **L2** | 다른 부서의 UI/입력/출력/데이터 계약·상태 표시·에셋에 영향 | 영향받는 부서에만 검토 요청, PR에 의견 기록 |
| **L3** | 승인된 세계관/게임 규칙·MVP 범위 변경, 공통 원장/시간·중대 통합 위험 또는 부서 간 심각한 충돌 | HQ 통합 영향도 검토, 필요한 Owner 결정·승인 |

최초 등급은 Issue와 티켓에 적고 작업 중 실제 영향을 발견하면 상향한다. L1이라도 강제 검사를 우회하지 않으며, L3가 모든 작업을 다시 Gate 2 전면 검토로 돌리는 것은 아니다.

## 6. 권한 위임의 안전선

Owner의 개별 티켓 승인에 `저장소/담당 부서/작업 ID/브랜치/허용 경로/Commit·Push·PR 각각의 허용 여부/유효 기간 또는 종료 조건/검증 요건/금지 동작`을 명시한다. 명시되지 않은 동작은 허용되지 않는다.

한 티켓에 권한을 부여했다고 해당 부서의 향후 모든 작업으로 위임이 확장되지 않는다. **main 직접 Push, Merge, 릴리스, 타 부서 영역 수정, CI 검사 우회**는 이 문서로 허용되지 않는다. 기획 또는 제작 범위 변경은 별도 Owner 승인이 필요하다.

## 7. 품질 완료와 첫 Stage 시범 평가

기존 티켓 상태 `BACKLOG→APPROVED→IN_PROGRESS→REVIEW→DONE`을 유지한다. PM-007의 **IMPLEMENTED/VERIFIED/ACCEPTED**는 품질 증거 수준으로 구분하며 코드 작성·PR 게시·Merge만으로 DONE 처리하지 않는다.

첫 Stage의 HQ 평가 항목:
- 기획 선행 대기와 반복 파일 전달·전 부서 중복 검토가 감소했는지
- 승인된 규칙과 UI/데이터 계약의 불일치·결함이 늘어나지 않았는지
- 실제 실행·AC 검증·통합 가능한 게임 산출물이 만들어졌는지
- 필수 Git 정책·Owner 최종 승인·부서 경계가 지켜졌는지
- Blocker가 Issue로 추적되고 소유자·해결 조건·차단 시점이 명확한지

**시범 기간은 작업일 숫자가 아니라 '첫 Stage 완료 또는 종료 검토 시점'**으로 한다. 평가는 '만든 문서 수'가 아니라 검증·인수 결과로 수행한다.
