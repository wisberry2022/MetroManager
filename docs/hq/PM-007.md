## 1. 목적, 경계 및 품질의 의미

본 문서의 목표는 **빨리 생성하는 것**이 아니라, 합의한 게임 경험을 일관되고 검증 가능한 구현물로 축적하는 것입니다. 기획·디자인·개발 각 부서가 전문 영역의 품질을 책임지고, HQ가 선행 의존성·통합 결과·범위·위험 및 승인 게이트를 조정합니다.

**적정 품질 = 해당 단계에서 승인된 목적·범위와 Acceptance Criteria(AC)를 충분히 충족하는 것**입니다. 무제한의 폴리싱, 게임 메커니즘·에셋 종류 추가, 추상화 확대는 품질 향상이라는 명목으로 자동 허용하지 않습니다. 새로운 범위가 필요하면 효과, 기존 승인 명세와의 차이, 테스트·통합 영향 및 Owner 결정 필요성을 RFC로 제시합니다.

Gate 2가 승인한 **MVP 8개 영역, MUST 11개, AC-01~10, 독립 VP-01/02**를 훼손하지 않습니다. Idea Library의 후보 기능은 MVP 범위가 아니며 본 문서로 승격되지 않습니다. 게임 실행/테스트/빌드/성능의 실증 없이 APPROVED 기획을 구현 완료로 표시하지 않습니다.

## 2. 일정·작업량 정책: 날짜보다 결과 중심

1. 인간 노동을 가정한 맨먼스·인일·8시간/일 추정치를 **AI 작업 완료일의 기계적 계산 근거로 사용하지 않습니다**. 기존 디자인 24~40 작업일 등은 역사적 가정/참고치이며 약속한 일정이 아닙니다.
2. 계획은 **단계(Stage) → 플레이 가능한 기능/Vertical Slice → 검증 가능한 작업 티켓 → 주차별 우선 과제**의 네 수준으로 구분합니다.
3. **주차는 고정 납기가 아닌 점검·재계획 주기**입니다. 미완료 자체는 실패가 아닙니다. 대신 어떤 구현물이 생겼는지, 어떤 테스트가 실패했는지, 무엇이 막혔는지, 다음 주에 무엇을 먼저 시도할지를 보고합니다.
4. 시간·자원은 무시하지 않습니다. 반복 실패, 토큰/사용량 한도, 도구 접근, 실제 검증·통합, Owner 승인 지연을 **위험/장애**로 기록합니다. 요청 없이 매 작업의 소요일이나 정확한 출시일을 강제하지 않습니다.
5. 작업 수·코드 줄 수·제작 이미지 수는 품질 KPI가 아닙니다. **실제로 검증된 기능, 통합 안정성, 재현 가능성, 누락/모순 감소**를 관찰합니다.
6. 품질을 이유로 범위가 계속 확대되면 기존 AC 충족에 필요한 결함 수정인지, 새로운 기능 요구인지 구분하고 후자는 RFC 및 Owner 승인으로 관리합니다.

### 2.1 단계별 완료 목표의 예시 (최종 기술 계획 아님)

| 예비 Stage | 통합 결과물(예시) | 선행 관계/부서 확인 |
|---|---|---|
| S1 규칙·입력 기준선 | 승인 명세/검수 데이터, 상태·UI 의미 계약 초안, 재현 기준 | 기획 의미 확인 + 개발/디자인 인터페이스 협의 |
| S2 행정·노선 조작 | 행정/관할 조회, 후보역 선택과 유효성 확인 | 기획 DATA → 개발 검증 → 디자인 가독성 |
| S3 시간·재무 기반 | 시간 진행과 C/R/F/K/A/B 장부, 미지급/도착 사건의 검산 | 승인 SEM/CLOSE → 개발 테스트 |
| S4 두 사업 취득·건설 | 제안·입찰 경로, 시공·시험·개통의 상태와 UI | S2/S3 기반, 디자인 상태 계약 |
| S5 운영·정산·통합 | 수요/운행/일일 보고/다음 사업 및 두 VP 플레이 검증 | S3/S4 기반, 부서 공통 인수 |

**위 순서는 HQ의 의존성 검토 출발점이지 개발팀·디자인팀의 확정 WBS나 주차 배정이 아닙니다.** 각 부서는 공식 Gate 2 승인본으로 자체 작업 분해·우선순위를 제시하고, HQ가 교차 의존성과 단계별 목표를 통합합니다.

### 2.2 주차별 운영 리듬

- **계획 시점:** HQ와 각 부서가 이번 주 가장 중요한 검증 목표 1~3개, 선행 조건, 미결 Owner 판단을 공유합니다.
- **실행 중:** 부서는 본인 영역의 독립 작업을 자율적으로 배치하고 관련 파일·커밋·테스트 증거를 작업 티켓에 남깁니다. 독립 작업만 병렬화합니다.
- **점검 시점:** `예정한 결과/실제 증거/미완료 원인/품질 위험/다음 우선순위`를 간결히 기록합니다. 완료를 위해 테스트·검수를 생략하지 않습니다.
- **다음 주:** 완료되지 않은 항목은 영향에 따라 유지·분할·재배치합니다. 장기 차단 항목에는 책임자, 필요한 결정, 목표 해소 단계가 있어야 합니다.
- **미완료의 평가:** 늦어진 것 자체는 실패가 아니지만, 장애를 은폐하거나, 선행 명세 없이 통합을 진행하거나, 근거 없이 반복 재작업하는 것은 관리 이슈입니다.

## 3. 부서별 품질 중점·최소 검증 기준

### 3.1 Planning — 세계관/설정 및 규칙 정합성

**목표:** 새로운 게임 기능이나 콘텐츠를 제안할 때 기존 승인 세계관·설정·경제/행정/시간 규칙과 충돌하지 않고, 플레이어 경험과 기존 시스템에 일관되게 연결되도록 합니다.

- **승인 기준 식별:** Gate 1, Gate 2 및 후속 승인 문서의 해당 ID·버전·SHA를 먼저 기록합니다. 과거 DRAFT·Idea Library를 확정 규칙처럼 사용하지 않습니다.
- **충돌 검사:** 새 기능이 기존 회사/행정 관할, 사업 취득·심사, 노선·운영, 자금·시간 사건, 실패/회복 규칙과 충돌하는지 비교합니다. 설정상의 이야기 모순과 **게임 규칙/데이터의 논리적 모순**을 모두 점검합니다.
- **충돌 기록:** `기존 ID/규칙 → 제안 항목 → 충돌 또는 비충돌 근거 → 영향받는 AC·VP·부서 → 수정 대안 → Owner 결정 필요 여부` 순서로 남깁니다.
- **완료 증거:** 기능 목적/비범위, 정상·실패·경계 사례, 상태 전이/규칙, 기존 명세와의 추적 관계, 개발·디자인 인수에 필요한 질문을 제출합니다. 기존 승인 규칙의 변경은 독단 확정하지 않습니다.
- **품질 결함 예:** 입찰 경로와 회사 제안 경로에 동일한 정부 심사 절차를 중복 부여, 행정상 관할과 지리 포함을 혼동, 종료 시각 비용을 중복 정산하는 설정 제안.
- **피해야 할 과잉 작업:** 아직 MVP에 필요 없는 세계관 세부 설정·아이템·이벤트를 무한 확장하거나, 정합성 설명 없이 새 게임 메커니즘을 추가하지 않습니다.

### 3.2 Design — 일관성·재사용·플레이어 경험

**목표:** 아트/레이아웃/상호작용의 일관성을 유지하고 불필요한 중복 제작을 막으며, 플레이어에게 혼란·읽기 어려움·불쾌감을 줄 **사용성 위험**을 근거 기반으로 식별합니다.

- **스타일 일관성:** 승인된 아트 바이블과 UI 가이드의 픽셀 밀도, 타일/색상/폰트/아이콘/레이아웃·상태 표기 원칙을 확인합니다. 미승인 시안은 공식 스타일로 간주하지 않습니다.
- **재사용 우선:** 신규 컴포넌트·아이콘·타일을 제작하기 전에 기존 목록/에셋/공통 결과 패턴을 비교하여 중복 여부를 기록하고, 동일 기능·상태는 가능한 한 재사용합니다. 다만 재사용 때문에 의미가 달라진 상태를 하나로 합치지 않습니다.
- **거부감의 정의:** 추상적 취향이나 근거 없는 집단 속성으로 판단하지 않습니다. 글자 크기/대비·클릭 영역·오류 복구·과도한 시각 자극·상태 구별·키보드 조작·정보 과부하 등 **관찰 가능 위험**으로 구체화합니다. 실제 사용자 테스트를 하지 않았다면 '사용성 PASS'를 주장하지 않습니다.
- **일관된 의미 표현:** `예상/실적`, `현재 자금/과거 마감 보고`, `비영업/신규 탑승 제한/기존 승객 이동 중`, `발생 비용/실제 지출/미지급`을 서로 혼동하지 않는지 확인합니다.
- **완료 증거:** 화면/상태별 사양, 재사용/신규 에셋 목록, 기획·개발 계약에서 받은 값/시점/허용 행동, 최소 가독성·오류/경계 상태 검토표, 미실행 목업/성능·사용성 테스트의 NOT_RUN 기록.
- **피해야 할 과잉 작업:** 승인된 최소 표현(집계+열차 이동/정차+승하차 아이콘)을 넘어 개별 시민 전원 애니메이션이나 새로운 고유 에셋을 품질 명목으로 무단 추가하지 않습니다.

### 3.3 Development — 실행 가능성·적정 확장성·기획 충실도

**목표:** Godot에서 실제로 실행되고 반복 테스트할 수 있는 기능을 만들며, 다음 기능을 안전하게 추가할 수 있도록 유지보수 가능한 구조를 확보합니다.

- **실행/검증:** 코드를 작성한 것만으로 완료하지 않습니다. Godot 프로젝트 로드, 관련 자동 테스트, 통합 플레이, Windows 빌드는 각각 별도 검증 항목으로 보고하며 수행하지 못하면 NOT_RUN과 원인을 기록합니다.
- **기획 추적성:** 구현·테스트가 어느 승인된 기능 ID, AC, VP, Owner 정책/세칙에 대응하는지 기록합니다. 세계관·사업 규칙·수익/비용과 UI의 실제 행동이 승인 명세와 다른 경우 변경 대신 RFC로 질문합니다.
- **적정 확장성:** 시간·경제·상태·UI 표현의 책임을 필요한 수준으로 분리하고, 안정적 식별자·재현 로그·데이터 계약·테스트 가능성을 고려합니다. 추후 고도화 가능성은 확인하되 **요청되지 않은 범용 프레임워크나 과도한 추상화는 개발 범위에 포함하지 않습니다**.
- **안정성:** 자금 불변식, 자정/동시각 경계, 중복 지급·비용 처리 방지, 기존 이동 중 승객의 완료, 분할/배속 동일 결과, 두 독립 VP의 성공·실패/복구 검증을 계획합니다. 테스트 결과는 입력·예상·실제·로그/스크린샷 등 증거와 연결합니다.
- **완료 증거:** 변경 파일, 실행 환경, 테스트 종류별 결과, 회귀 범위, 알려진 결함, 다음 의존성, 미검증 항목 및 실행 가능한 인수 빌드(단계상 해당될 때).
- **피해야 할 과잉 작업:** 아직 승인되지 않은 신용/부채 모델, NPC 개별 AI, 다중 도시, 취소/정산 토글 등을 '확장성 확보' 명목으로 구현하지 않습니다.

## 4. 작업 티켓과 완료 상태의 품질 계약

각 부서는 자신의 전문 영역에서 작업을 자율적으로 분해하지만 모든 티켓에 다음을 기록합니다.

| 필드 | 기재 사항 |
|---|---|
| 작업 ID·담당·승인 상태 | PM/PLN/DSG/DEV 식별자, Owner 또는 위임 승인 범위 |
| 목표·플레이어 가치 | 왜 현재 단계에서 필요한가, 화면/행동과 어떤 관련인가 |
| 입력 기준선 | 승인 문서 경로·버전·정확한 Git SHA와 기능/AC/VP ID |
| 선행·교차 의존성 | 완료되어야 하는 다른 부서의 데이터·화면·코드 |
| 포함/제외 범위 | 최소 검증 작업, 후속 고도화로 분리할 것 |
| 산출물·완료 조건 | 실제 파일/씬/화면/동작과 관찰 가능한 조건 |
| 품질 검증 및 증거 | 테스트 종류, 입력/예상/실제, 이미지/로그/커밋 링크 |
| 결함/RFC·이월 | 모호성, 영향도, 담당, 해소 시점, 필요 Owner 승인 |
| 미실행 | 실행하지 않은 게임/빌드/사용성 테스트는 NOT_RUN과 이유 |

**티켓 흐름** `BACKLOG → APPROVED → IN_PROGRESS → REVIEW → DONE`는 기존 운영 규정을 유지합니다. `IMPLEMENTED / VERIFIED / ACCEPTED`는 아래 **품질 증거 수준**을 표시하는 보조 개념이며 기존 티켓 상태를 자동 대체하지 않습니다.

- **IMPLEMENTED:** 담당 산출물 생성·연결 완료. 테스트 미실행 또는 실패는 여기서 멈춥니다.
- **VERIFIED:** 해당 단계·부서의 합의된 검증과 관련 회귀 검증 통과, 증거 제출. 실행할 수 없는 검증은 통과로 간주하지 않습니다.
- **ACCEPTED:** HQ/Owner 등 해당 권한자가 수용 기준과 증거를 확인하고 인수 승인. 부서 자체 완료 선언/PR 병합만으로 이 상태가 되지 않습니다.

품질이 충분하다는 의미는 **'아무 결함도 없다'가 아니라 해당 단계에서 합의한 필수 AC가 충족되고, 잔여 결함의 위험이 식별되어 수용되었다**는 것입니다. 심각한 오류·주요 승인 규칙 불일치·재현 불가 상태에서는 ACCEPTED로 변경하지 않습니다.

## 5. 권한 경계, 변경 통제 및 Git

- 기획은 게임 규칙·세계관의 상세 판단, 디자인은 표현·UX·재사용 판단, 개발은 기술 구조·검증 판단을 담당합니다. HQ는 **범위·우선순위·부서 간 선행 의존성·리스크·인수·Gate 판단**에 집중하며 전문 세부 설계를 대신하지 않습니다.
- Owner의 핵심 기능/범위 변경과 Gate 승인·릴리스 최종 권한은 유지합니다. 기존 승인 기획과 충돌하면 변경 영향·대안 및 승인 필요 사항을 `RFC`로 상정합니다.
- Gate 2 승인본은 검토 기준선이지 각 개발/디자인 작업의 자동 착수 허가가 아닙니다. Gate 3 작업 티켓과 부서별 실행 권한을 별도로 확인합니다.
- 부서별 문서의 작성·수정은 본인 소관 Git 경로에서만 수행하고, 신규 업무별 `codex/<TASK-ID>-...` 브랜치·정형 Commit/PR·CI·Owner Merge 승인 절차를 유지합니다.
- ChatGPT/Codex 세션 간 자동 동기화를 가정하지 않습니다. 인수인계는 **문서 경로/버전/승인 상태/SHA/티켓/변경 요약**을 명시하고 수신 부서의 확인을 받습니다.

## 6. 각 부서가 숙지·회신할 사항 (Owner가 이 문서를 승인한 후)

본 문서가 main에 병합되어도 **각 에이전트의 별도 채팅에 알림·지침이 자동 적용되지 않습니다.** Owner/HQ가 링크와 적용 승인 근거를 전달하며 각 부서는 작업 시작 전 직접 최신 공식 문서를 읽어야 합니다.

| 수신 | 확인할 책임·응답 |
|---|---|
| Planning | 세계관/기존 명세 충돌 점검 방식, 이슈/대안 표기, 기능 ID/AC 추적을 확인하고 본인 부서의 Gate 3 작업 분해안을 제출 |
