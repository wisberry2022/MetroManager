### 3.1 W04A — 공공입찰 및 사업 확보

**주관:** Development
**의미 검토:** Planning
**화면 검수:** Design
**연결:** F-03, F-10, F-11

기준 사업은 C01 시청이 발주한 B01 공고다. 승인된 P-A의 6역 정상 노선 예시를 사용한다.

| 검토 항목 | 승인된 입력·동작 |
|---|---|
| 공고 | B01, B02 및 관할 밖 B-X의 노출·비노출 규칙 |
| 공고 조건 | 발주자, 관할, 고정 운임100, 정부 사업비800000, 공사기간2880분 |
| 접수기간 | 시작일 06:00부터 다음 날 06:00 직전 |
| 응찰 자격 | 관할, 계약 중복, 공기 이행 가능성 등 승인 조건 |
| 점수 | 7×이행능력 + 3×재무점수 정수 비교 |
| 정상 판정 | 플레이어86, 경쟁자80 → 낙찰 |
| 동점 | 공고의 사전 공개 순위에 따라 경쟁자 우선 |
| 계약 | 낙찰 후 정부 재심사 없이 유효 계약·정부 지급 |
| 실패 | 마감, 탈락, 자격 미충족, 중복 명령, 동일 종료 회차 재응찰 거부 |

DEV는 판정 당시 자격·점수·고정 조건·결과를 재현 가능한 스냅샷으로 보존한다.

응찰 접수, 낙찰 판정, 계약 효력, 정부 지급은 서로 다른 의미를 갖는다. 동일한 명령이나 결과 재수신이 중복 계약·중복 지급을 만들 수 없다.

입찰은 승인된 공개 점수와 동점 규칙을 사용하며 새로운 무작위 낙찰 규칙을 추가하지 않는다.

**완료 증거:** 정상 B01 낙찰·계약과 실패/동점/마감/중복 경계의 자동검증, 실제 공고·응찰·결과·계약 UI 조작, Planning 의미 수용.

### 3.2 W05 — 시공·시범운행·안전검증·개통

**주관:** Development
**의미 검토:** Planning
**화면 검수:** Design
**연결:** F-05, F-10, F-11

주요 VS-01 성공 경로는 **표준 공사**다.

| 구분 | 승인된 값 |
|---|---|
| 표준 공사 | 600000 / 2880게임분 |
| 빠른 공사 | 720000 / 1440게임분 |
| 기성 | 누적 floor 차액 방식 |
| 시범운행 | 60게임분 |
| 안전검증 | 60게임분 |
| 빠른 공사 첫 안전 결함 | 1개 |
| 결함 수리 | 20000 / 30게임분 |
| 안전 재시험 | 60게임분 |

사업 계약 및 정부 지급 전에 착공할 수 없다.

각 기성 지급은 해당 사업 제한금 R과 미집행 회사 예약 K를 정확하게 사용해야 한다. 타 사업 R/K의 전용은 허용하지 않는다.

시간 경과로 공정률이 100%가 되더라도 최종 기성 지급이 실패하면 완공으로 처리할 수 없다.

시범운행과 안전검증을 별도 절차로 유지하며, 두 검증의 유효한 통과 및 개통 조건 충족 전에는 일반 승객의 영업 운임이 발생하지 않아야 한다.

**Stage 2 최소 검증 구성:** 표준 공사의 정상 완주를 실제 UI로 확인한다. 빠른 공사의 안전 결함·수리·재시험과 공정 자금 부족·중단·재개는 별도의 자동 회귀 및 필요한 상태 UI 검증으로 확보한다. 빠른 공사의 독립 전체 사업 E2E까지 Stage 2에서 반복 수행할 의무는 추가하지 않는다.

**완료 증거:** 공정별 발생·실제 지급 원장, 공사 상태 전이, 시험·안전 상태 및 오류 복구, 개통 전 일반 영업 차단, 실제 GUI에서의 공사·검증 조작.

**화면 검수:** Design
**연결:** F-05, F-07 부분, F-10, F-11

실제 열차 이동·정차와 역 승하차의 경량 시각 피드백을 제품 UI에서 제공한다. 이는 집계된 시뮬레이션을 표현하는 장치이며, 연출 자체가 승객·운임·운영비를 생성해서는 안 된다.

운행 정지·영업시간 종료·미지급 발생으로 신규 승객 탑승이 제한되더라도 기존 이동 중 승객은 예정된 조건에 따라 도착할 수 있다.

도착 운임은 그 시각 회사 자유현금으로 인식하고 기존 B를 우선 정산한다. 미지급 정산이 완료돼도 영업시간·다음 운행비·다른 조건을 재검사해야 신규 탑승이 재개된다.

첫 일일 보고서는 **실제 완료 통행과 영업 실적이 발생한 유효 보고**를 VS-01 정상 완주 증거로 사용한다. 영업 0분 또는 완료 통행 0건 보고도 정상적으로 표시할 수 있어야 하지만, 그 자체만으로 VS-01 성공을 선언하지 않는다.

이후 플레이어는 첫 사업의 실적을 확인하고 다음 사업 공고 또는 후보 조회 화면으로 진입할 수 있어야 한다. 두 번째 사업의 실제 수주·시공·개통은 Stage 2 성공 조건에 포함하지 않는다.

**완료 증거:** 실제 요청/탑승/미탑승/이동 중/도착, 운임·비용·미지급·정산, 만족도, 고정 일일 보고, 다음 사업 조회의 자동 및 GUI 통합 검증.

Stage 2의 정상 VS-01에 필요한 조작은 실제 UI 버튼 또는 명시적 사용자 입력 경로로 제공한다.

테스트 전용 자동 호출이나 스크립트 명령만으로 입찰·착공·검증·다음 사업 이동을 완료할 수 있다면 UI 통합 인수에는 불합격이다.

DEV는 같은 `snapshot_revision`에서 권위 값·허용 행동·사유를 공급하고, Design은 필요한 상태만 검토한다. 화면이 경제 금액·입찰 점수·운행 결과를 독자적으로 다시 계산하지 않는다.

UI는 다음을 구별해야 한다.

- 미수신·미계산·실패·정상 0
- 대기 명령·성공·거부 및 효력 시각
- 현재 자금·계약 당시 판정·과거 고정 보고
- 발생 비용·즉시 현금 지급·과거 미지급 후정산
- 시공 중·자금 중단·검증 실패·개통 완료
- 정상 영업·신규 탑승 제한·기존 승객 이동 중·도착·재개 가능

**디자인 품질 범위:** 실제 사용 가능한 저충실도 내지 필요한 최소 표현의 UI를 합격 기준으로 한다. 고충실도 시각 스타일이나 최종 픽셀 아트를 Stage 2 필수 조건으로 추가하지 않는다.

## 4. 대표 VS-01 원장 검산

기본 입력은 독립된 초기 회사 상태다.

| 사건 | 총현금 C | 제한자금 R | 자유현금 F | 예약 K |
|---|---:|---:|---:|---:|
| 게임 시작 | 1,000,000 | 0 | 1,000,000 | 0 |
| B01 계약·정부 지급 800,000 | 1,800,000 | 800,000 | 1,000,000 | 0 |
| 표준 공사비 600,000 전액 기성 집행 | 1,200,000 | 200,000 | 1,000,000 | 0 |

위 수치는 **공사 완료 직후, 일반 영업 운임·운영비가 반영되기 전** 정상 기준이다.

남은 R=200000은 회사 자유현금으로 자동 전환되지 않는다.

이후 실제 완료 통행 수 n, 실제 현금 운임수입, 발생 운영비 및 그 현금 지급은 실행한 게임 명령·시각에 따라 달라진다. 따라서 일일 영업 실적을 임의의 고정 금액으로 합격 처리하지 않는다.

최종 인수는 시점별 C/R/F/K/A/B와 정부 매출·공사 비용·운임 매출·운영비 발생·현금 지급이 실제 원장과 일치하는지 비교해야 한다.

- 잘못된 공고·자격·마감·중복 응찰로 계약·정부 매출이 중복 발생하지 않는다.

- 23:59 탑승한 8명이 다음날 00:09 도착할 경우 완료 운임은 다음날 800이며 추가 잔여 운행비는 0이다.
- 전일 확정 보고는 이후 계약·도착·정산 사건으로 변조되지 않는다.
- B 정산은 운영비를 다시 발생시키지 않고, 신규 탑승 재개는 모든 영업 조건을 충족해야 한다.
- 조회·반복 클릭·거부·늦은 결과로 게임 시간·원장·수요·명령 효과가 중복되지 않는다.

### 검증 수준 구분

**DEV 자동검사:** 정적 기대값뿐 아니라 실제 Godot 규칙·회귀 테스트를 실행한다.

**Design 독립 인수:** 실제 사용성과 상태 표현을 재검수한다. 내부 불변식은 적절한 자동 증거를 수용할 수 있지만 실제 조작 항목을 스크린샷이나 정적 검토만으로 대체하지 않는다.

**Planning:** 승인 의미와 달라진 계산·상태·행동에 한정해 검토한다. 기술 설계나 Godot 재실행까지 담당하게 하지 않는다.

**HQ/Owner:** 각 증거의 범위·소유·미실행·결함·후속 이관을 통합하여 Stage 결과를 판단한다.

VS-01 자동검사의 성공만으로 S2-10의 실제 GUI 경로 완주를 선언하지 않는다.

## 10. 품질 검토·권한 절차

PM-008의 운영 규칙을 유지한다.

**L1 — 내부 소관 검증:** 승인된 범위 내 변경을 자체 검증.

**L2 — 영향 부서 계약 검토:** DEV↔Design의 실제 상태 공급·화면 인수, DEV↔Planning의 승인 규칙 의미 차이만 검토.

**L3 — 공통 영향 및 Owner 결정:** 승인 경제·시간·게임 규칙·MVP 범위 변경, 중대한 원장/운행 통합 위험이나 해결되지 않은 부서 충돌을 HQ가 검토해 필요한 Owner 결정에 상정한다.

기존 승인된 SEM-01~03을 그대로 구현하는 것만으로 새로운 게임 정책 승인을 매번 요구하지 않는다. 다만 공통 원장에 영향을 주는 구현은 영향 범위의 회귀와 검증 책임을 명시해야 한다.

각 실행 티켓에는 다음 계약을 기록한다.

- 정식 작업 ID·담당·기준 main 및 관계 기능/AC/S2-ID
- 포함·비범위·최초 차단 시점
- 공급·소비 부서·리뷰 수준 및 완료 증거
- Owner가 승인한 파일 경로·브랜치·행위·유효 범위
- 실제 테스트 명령·버전·입력·기대·실제·종료 코드·NOT_RUN
- PR head SHA와 `policy`·`department-policy`, 결함·회귀 영향
- 후속 F-ID 연결 및 남은 책임

작업 상태는 `BACKLOG → APPROVED → IN_PROGRESS → REVIEW → DONE`으로, 품질 수준은 `IMPLEMENTED / VERIFIED / ACCEPTED`로 별도 관리한다.

작업 브랜치는 최신 main에서 분리한다. DEV-014로 승인된 검증된 무충돌 base-sync 예외를 보존하며 임의 merge, 충돌 무시, 강제 push, CI 우회를 허용하지 않는다.

**Stage 2 계획 승인만으로 기능 구현·디자인 에셋 제작·Commit·Push·PR·main 병합 권한은 발생하지 않는다.**

## 12. Stage 2 통합 인수 순서

1. **Development 자체 검증:** W04A·W05·W06 정상·실패·경계의 실제 Godot 자동 회귀와 headless 프로젝트 검증.
2. **UI 통합:** 제품에서 입찰부터 다음 사업 조회까지 실제 조작 가능한지 확인.
3. **Design 독립 검수:** 상태·원인·허용 행동·오류 복구 및 실제 GUI 자료 수용.
4. **Planning 정합성:** 승인된 규칙과 달라진 항목, 중요 경제·시간·심사 의미에 한정한 검토.
5. **HQ 통합 심사:** S2-01~11 결과, 누락·NOT_RUN·회귀·F-ID 추적·CI/PR 병합 상태 확인.
6. **Owner 최종 수용:** Stage 2 결과에 대한 명시적 승인. 필요하면 범위가 한정된 조건부 수용을 제안할 수 있으나 완료 기준을 임의 완화하지 않는다.
7. **공식 종료:** Owner 결정과 S2 종료 기록을 승인된 Git 절차로 반영한 후 DONE 여부 결정.

원격 PR 병합이나 자동 테스트 PASS 하나만으로 Stage 전체를 종료하지 않는다.

## 13. 실행 우선순위 및 Owner 결정 항목

### 첫 실행 우선순위

**우선 1 — W04A:** 정상 사업 확보와 중복·마감·자격 경계. 이후 W05가 실제 계약 상태를 소비할 수 있게 한다.

**우선 2 — W05:** 정상 표준 공사와 자금 보호, 시험·안전의 독립 통과. 이후 W06이 실제 개통 상태를 소비할 수 있게 한다.

**우선 3 — W06 및 UI 통합:** 실제 요청·탑승·도착·운임·일일 보고·다음 사업을 연결하고 한 경로로 검증한다.

Design과 Planning의 필요한 산출물은 각 통합 시점보다 앞서 준비하고, DEV의 독립 모델 구현과 병렬 추진한다.

### 현재 결정과 다음 실행

Owner가 두 트랙 구성·S2 인수·협업 가이드를 승인했다. 본 문서의 main 병합은 별도 결정이다. 부서별 실행 티켓은 기존 유효한 승인 범위를 확인하고, 없으면 구체 범위·경로·기간·제작/Git 동작의 승인을 확보한다. 이번 HQ 문서 작성으로 각 부서에 메시지를 발송하거나 Issue를 변경하지 않는다.

Stage 2 실행·S2-01~11·S2-D01의 실제 검증은 아직 NOT_RUN이다. HQ는 각 티켓의 head·검증 수준·인수/차단·남은 F-ID를 연결하여 결과를 제출하고 Owner 최종 수용을 기다린다.
