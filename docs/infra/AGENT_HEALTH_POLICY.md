- 기준: `AGENTS.md`, `docs/engineering/DEPARTMENT_WORKFLOW.md`, `docs/hq/PM-008.md`, `docs/planning/PLN-001_GATE2_FINAL_APPROVAL.md` (실행 시 최신 승인 상태 재확인)

## 1. 목표와 계측 한계
오래된 채팅의 컨텍스트 초과를 추측하는 대신, **승인 결정의 정확성·현재 업무의 연속성·권한 및 검증 경계·반복 오류**로 업무 지속 가능성을 판단한다. ChatGPT 웹 채팅/Codex의 실제 남은 컨텍스트 토큰, 내부 압축 상태, 전체 숨은 컨텍스트는 GitHub 이력으로 직접 측정할 수 없다. 메시지 수·PR 수·경과일만으로 과부하를 판정하지 않는다.

증거: (a) Owner 승인 기록과 Git 버전/SHA (b) 현직 자기보고 (c) Issue·PR·티켓 상태 (d) 검증된 오류·교정 이력 (e) 필요한 경우 독립 재진술·후임 수용 시험. 현직 자기평가를 그대로 INF 확정 점수로 채택하지 않는다.

## 2. 직무 분리
| 주체 | 책임 |
|---|---|
| INF | 검사 규격·증거 대조·위험 판정·Owner 교체 권고·후임 수용 검증 |
| 현직 부서 | 근거 있는 업무 스냅샷, 오답/정정 사실, 인계 패키지 작성 |
| 후임 | 공식 원본 독립 확인, 수용 질문 응답, 첫 안전한 행동 명시 |
| PM | Stage·의존성·진행 PR/티켓 및 전환 시점 조정; 전문 결정/INF 점수 대행 금지 |
| Owner | 교체 착수·후임 임명·Git 권한 재부여·main 병합·릴리스 최종 결정 |

부서 전문 경계는 기존 규정 그대로다. INF가 다른 부서의 임시 승인, Git 권한 이전, 업무 완료 판정을 자동 생성하지 않는다.

## 3. 점검 주기 및 트리거
- 최초 도입 4부서 기준선: 각 현직의 보고 수집 → INF 독립 교차 검증.
- 정기: PM의 주간 점검 또는 Stage 시작·종료 시점에 연계한 **경량 확인**. 매번 전체 4개 영역을 재채점할 의무는 없으며 변경·위험이 있으면 정밀 진단.
- 수시: 공식 결정 반복 오인, 허가 없는 변경, 현재 티켓/PR 추적 상실, 동일 완료 업무 반복, 중요한 보고의 검증 범위 과장, 장기 차단, Owner/PM/현직 요청.
- 긴급: 승인 없는 고위험 쓰기, 자료 파괴 가능성 또는 세션 접근 불가 발생 → 관련 쓰기 중단 권고, Git 최신 승인 원본 재확인, Owner 보고.

이 정책만으로 예약 검사·자동 모니터링·다른 채팅으로 직접 메시지 발송이 시작되지는 않는다.

## 4. ACHC 평가
4영역 각각 0~4점. 0=중대 불일치, 1=반복 불일치, 2=일부 누락, 3=대체로 근거 일치, 4=충분한 근거와 재현 확인. 확인할 수 없는 항목은 **N/A**로 기록하고 0점 처리하지 않는다.

| 영역 | 가중치 | 검증 질문 |
|---|---:|---|
| A 공식 맥락 정확성 | 35 | 현재 승인 상태·버전·결정·제외 범위를 정확히 재구성하는가 |
| B 작업 연속성 | 30 | 티켓/Issue/PR·미결·차단·다음 작업을 근거로 추적하는가 |
| C 일관성 및 권한 | 25 | R&R·Owner 승인·미검증/실행 결과를 구분하는가 |
| D 부담 위험(역점수) | 10 | 지속적인 맥락 누락·불필요한 반복 오류의 검증 증거가 없는가 |

D의 **4점은 낮은 부담 위험**, 0점은 높은 부담 위험. 단순한 최신 원본 재열람이나 정상적인 정책 수정에 따른 재검토는 오류가 아니다.

점수 = `100 × Σ((영역점수 / 4) × 가중치) / Σ(평가 가능 영역 가중치)`.
A·B·C 중 하나라도 N/A면 총점 `NOT_ASSESSED`. D만 N/A일 때는 A/B/C의 가중치 합 90으로 정규화하고 평가 제외를 표시한다. 숫자는 **관찰 근거의 적합성 지표**이지 실제 남은 토큰 비율이 아니다.

시범 참고 구간(절대 자동 판정 아님): 85~100=유지, 70~85 미만=주의, 50~70 미만=인계 준비 검토, 0~50 미만=교체 권고 검토. 낮은 점수라도 즉시 자동 교체하지 않고, 높은 점수라도 마일스톤 경계에서 예방적 인계 준비를 할 수 있다. 점수 구간과 최종 권고가 다르면 사유를 명시한다.

**점수보다 우선하는 중대 검토 조건:** DRAFT를 승인으로 오인, 필수 승인 없이 main/merge/릴리스 진행, 실행하지 않은 게임 테스트를 PASS로 선언, 타 부서 결정 무단 확정, 중요한 자료 파괴 위험. 사고 사실·영향·재발 여부를 확인하고 Owner 판단을 요청하며, 단일 오류의 원인을 무조건 컨텍스트 소진으로 단정하지 않는다.

## 5. 진단 절차
`REQUESTED → SELF_REPORTED → CROSS_CHECKED → INF_RECOMMENDATION → OWNER_DECISION`.
1. Owner/PM/INF가 대상 세션, 기준 시각, 이유와 범위를 정한다.
2. 현직은 `AGENT_HEALTH_REPORT_TEMPLATE.md`에 따라 자기보고. 측정 불가를 임의 점수로 채우지 않는다.
3. INF는 최신 승인 원본과 Issue/PR/티켓을 별도로 조회해 대조한다. 과거 시점에 맞았던 기록의 노후화와 실제 기억 착오를 구별한다.
4. INF는 `AGENT_ASSESSMENT_TEMPLATE.md`에 A/B/C/D, 관찰 사실·한계·최종 권고를 작성한다. 보안상 상세 평가문은 Owner 제한 전달.
5. PM은 전환 시점·의존성을 검토, Owner가 교체 여부 결정. 진단은 기존 업무 권한을 정지시키거나 새 세션을 자동 생성하지 않는다.

## 6. 세대교체 게이트
`RECOMMENDED → OWNER_AUTHORIZED → HANDOFF_PREPARED → SUCCESSOR_BOOTSTRAPPED → ACCEPTANCE_VERIFIED → PM_SWITCH_CONFIRMED → OWNER_TRANSFER_APPROVED → RETIRED`.
- 현직이 접근 가능하면 진행 중 작업을 가능한 한 안전한 PR/티켓 경계에서 멈추고 4계층 인계: 역할·금지/권한 → 승인 Git 원본 → 작업 스냅샷 → 필요 시 상세 이력.
- 후임은 **새 세션**에서 Git 기준선·현직 인계 문서를 읽고 승인/비승인·역할·현재 업무·권한·다음 행동을 자신의 말로 재구성한다. 과거 채팅 전체 주입은 기본값이 아니다.
- 수용: `AGENT_HANDOFF_TEMPLATE.md`의 CRITICAL 전부 PASS, NORMAL 80% 이상 PASS, 근거 링크·SHA 확인. 불명확하면 보완 후 재시험한다.
- 기존 티켓의 Commit/Push/PR 권한과 로컬 환경 상태는 후임에 자동 승계되지 않는다. Owner가 신규 담당·권한을 승인하고 PM이 업무 의존성과 전환 시각을 확인해야 실제 담당 전환된다.
- 현직은 자동 삭제하지 않고 참조 가능한 이력으로 유지한다. 검증 실패 시 후임 쓰기 중단, 안전한 기존 세션 또는 승인된 Git 원본으로 복구한다.

## 7. 비상 복구와 보안
현직에 접근 불가하면 Git의 최신 **승인된** 원본·PR·티켓을 사용한다. 로컬 미커밋 변경·채팅 전용 결정은 `UNKNOWN`/`NOT_VERIFIED`로 표시. 개발 환경(worktree·로컬 변경) 점검은 개발 소관. 인계 문서에 비밀값·내부 추론·개인 대화 전문을 수록하지 않는다.

**공개 Git:** 운영 규정·빈 양식·식별 가능한 공개 업무 근거만. **Owner 제한 자료:** 개별 진단 점수·오류·비공개 세션 식별자·개별 인계의 비공개 상세. 공개 필요성이 생기면 별도 Owner 검토 후 최소화한다.

## 8. 시범 회고
첫 Stage 종료 또는 첫 실제 교체 수용 시험 이후, INF는 오탐·누락·인계 실패·문서 유지 비용을 평가해 임계값 변경을 RFC/PR로 제안한다. 승인되지 않은 자동화, 정책/CI 완화, 게임 범위 변경은 이번 작업에 포함되지 않는다.
