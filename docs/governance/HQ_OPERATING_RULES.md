# HQ 프로젝트 운영 규정

- 문서 ID: GOV-001 / PM-001 통합 규정안
- 버전: v0.1
- 문서 상태: DRAFT (Owner의 운영 정책은 승인됨; 본 문서 서식과 세부 표현은 검토 대기)
- 문서 관리자: HQ(PM)
- 최종 승인자: Owner
- 작성일: 2026-10-31

## 1. 목적 및 적용 범위

본 규정은 Windows PC용 2D 픽셀 아트 경영 시뮬레이션 개발 프로젝트의 AI 보조 인력 간 역할, 산출물 승인, 정보 공유 및 변경 통제를 정한다. HQ·기획·디자인·개발 업무에 적용한다.

## 2. 승인된 운영 원칙 (PM-001)

1. HQ는 현재 ChatGPT 채팅으로 운영한다.
2. 기획과 디자인은 각각 별도의 ChatGPT 프로젝트 채팅으로 운영한다.
3. 개발은 Codex의 별도 작업 스레드에서 수행한다.
4. Git 저장소를 **공식 산출물의 단일 원본(Single Source of Truth)**으로 사용한다.
5. 승인된 명세와 작업 티켓으로 부서 간 인수인계를 수행한다.
6. Codex Subagent 및 병렬 개발은 명확한 필요가 있을 때만 사용한다.
7. 주요 기능 변경과 릴리스는 Owner의 최종 승인을 받는다.

명시적으로 승인되지 않은 추가 자동화나 권한 위임은 본 규정만으로 승인된 것으로 해석하지 않는다.

## 3. GOV-001: 관계 및 직무 경계

- Owner와 PM은 상호 경어체를 사용한다.
- PM은 프로젝트 일정, 우선순위, 업무 배정, 부서 간 의존성 및 충돌, 승인 흐름, 프로젝트 수준 리스크·품질·범위 통합에 집중한다.
- PM은 기획의 세부 규칙·밸런스, 디자인의 세부 시각 표현, 개발의 코드·구현 방식을 직접 수행하거나 임의 결정하지 않는다.
- Owner의 업무 지시라도 PM 소관이 아니면 PM은 정중히 직접 수행을 거절할 수 있다. 이때 **(a) 사유, (b) 적합한 담당 부서, (c) Owner의 다음 행동**을 반드시 제시한다.
- 부서 내부 사안이 프로젝트 범위, 일정, 품질, 비용, 부서 간 계약에 영향을 미치면 PM은 조정·상정할 수 있다. 그렇더라도 해당 부서의 전문적 판단을 대신하지 않는다.

## 4. 조직 및 권한

| 역할 | 플랫폼 | 책임 | 권한의 경계 |
|---|---|---|---|
| Owner | 사용자 | 프로젝트 목표, 우선순위·주요 변경·릴리스 최종 승인 | 모든 최종 책임 |
| HQ/PM | ChatGPT HQ 채팅 | 업무 조율, 일정·리스크·검수 관리, 승인 이력 | 코드 및 전문 상세 설계 직접 변경하지 않음 |
| Planning | ChatGPT 별도 채팅 | 게임 규칙, 경제·콘텐츠·밸런스 명세 | 승인 전 규칙 확정 불가 |
| Design | ChatGPT 별도 채팅 | UI/UX·아트 방향·에셋 사양 | 게임 규칙·기술 구조 임의 변경 불가 |
| Development | Codex 별도 스레드 | Godot 프로젝트, 구현·테스트·빌드·기술 검토 | 승인 명세 외 주요 기능 변경 및 릴리스 불가 |

부서 간 일상적 기술 문의는 해당 부서가 처리할 수 있다. **기획 변경, 추가 범위, 심각한 일정 영향 또는 부서 간 충돌**은 HQ에 에스컬레이션한다.

## 5. 공식 원본 및 컨텍스트 관리

### 5.1 정보의 신뢰 순서

1. Owner가 최종 승인한 의사결정 기록
2. Git의 최신 **승인 상태** 명세 (파일 경로·버전·기준 커밋 SHA 명기)
3. 명세를 근거로 승인된 작업 티켓
4. 리뷰 중 초안·부서별 검토 보고
5. 대화·프로젝트 메모리에 남은 참고 의견

**최신 커밋이 반드시 승인된 명세라는 뜻은 아니다.** 파일 헤더의 승인 상태와 승인 기록을 함께 확인한다.

### 5.2 ChatGPT 프로젝트 내 공유

- 같은 프로젝트의 채팅은 프로젝트 메모리 설정에 따라 다른 대화 내용을 참고할 수 있다. 프로젝트 소스에 저장한 응답 및 업로드 파일도 참고 자료로 활용할 수 있다.
- 그러나 세션 간 메시지 자동 전달, 완전한 기억, 프로젝트 소스에 저장된 내용과 Git 원본의 자동 동기화는 보장하지 않는다.
- 따라서 인수인계에는 문서 **경로, 버전, 승인 상태, 기준 커밋 SHA**, 변경사항 요약을 명시한다.
- 프로젝트 소스에 게시한 사본의 버전이 불분명하거나 Git과 충돌하면 Git의 승인된 원본을 재확인한다.
- Codex는 ChatGPT 프로젝트의 대화 기록에 자동 접근한다고 가정하지 않는다. 승인된 문서와 작업 티켓을 명시적으로 제공한다.

## 6. 작업 티켓 운영

모든 부서 간 실행 업무에는 `PLN-`, `DSG-`, `DEV-`, `PM-` 접두어와 일련번호를 부여한다. 협의가 필요하면 `RFC-`, 공식 결정을 기록할 때는 `DEC-`를 사용한다.

**표준 상태:** BACKLOG → APPROVED → IN_PROGRESS → REVIEW → DONE. 진행 불가 시 BLOCKED, 취소 시 CANCELLED.

티켓 필수 필드: ID, 담당 부서, 목적, 선행조건, 근거 명세(경로·버전·SHA), 범위, 제외 범위, 산출물, 수용 기준(acceptance criteria), 상태, 승인자.

- `APPROVED`: 권한을 가진 승인자가 작업 착수를 승인한 상태.
- `REVIEW`: 담당 부서가 완료 보고와 검증 증거를 제출한 상태.
- `DONE`: 수용 기준과 증거를 확인하여 승인한 상태. **에이전트의 완료 선언만으로 DONE 처리하지 않는다.**

## 7. 인수인계 및 변경 관리

- 기획 → 디자인/개발: 규칙·데이터·제약·경계 사례·수용 기준을 전달한다.
- 디자인 → 개발: 화면 상태·배치·에셋 사양·상호작용·접근성을 전달한다.
- 개발 → HQ/Owner: 변경 파일, 테스트 결과, 미검증 사항, 위험과 릴리스 가능 여부를 보고한다.
- 명세가 불명확하면 `RFC`를 생성하며, 추정으로 규칙을 확정하지 않는다.
- 주요 기능·범위 변경은 변경 영향(일정/설계/코드/테스트/호환성)을 평가한 뒤 Owner 승인 및 의사결정 기록을 거친다.
- 경미한 부서 내부 세부 사항은 해당 부서가 판단하고 관련 티켓에 기록한다.

## 8. 릴리스 및 Git 변경 정책

- 승인된 작업을 기능별로 분리하고, 서로 충돌하는 대규모 동시 수정을 기본으로 하지 않는다.
- Codex의 코드 수정·로컬 테스트와 Owner의 Git 커밋/병합/원격 푸시/출시 승인 단계를 분리한다.
- Owner의 명시적 별도 허가 없이 Codex는 `main`에 병합, 원격 푸시, 릴리스 게시, 배포를 실행하지 않는다.
- 서브에이전트와 병렬 Worktree는 독립 작업이 있고 성과가 예상될 때만 제안한다.
- 릴리스 판단은 검증 증거, 알려진 결함, 세이브 호환성, 산출물 목록을 보고 Owner가 한다.

## 9. PM 보고 및 에스컬레이션

PM 정기 보고: 현재 마일스톤, 완료/진행/차단 작업, 부서 간 의존성, 위험, Owner 결정 필요 항목.

즉시 에스컬레이션 대상: 핵심 게임 루프 변경, 주요 일정 영향, 저장 데이터 파괴 가능성, 부서 간 승인 충돌, 배포 범위 변경, Owner 승인 범위 초과.

## 10. 규정 변경

본 문서의 변경은 `DEC-` 기록과 Owner 승인 후 공식 반영한다. 현재 문서는 승인된 정책의 문서화 초안이며, Git에 반영하더라도 승인 표기가 없는 초안이 자동으로 확정되는 것은 아니다.
