## 1. 결론 및 판정 범위

1차 지적의 대부분이 구체적인 추천 모델과 AC로 반영되었다. 행정 부모·관할 무결성은 설계 검토 수준에서 해소되었다. 두 사업 경로, 제한자금, 시간 사건, 실패 복구, 반복 검증의 기본 구조는 기술적으로 구현 가능하다. MUST 11개 및 두 VP를 제거할 이유는 없다.

다만 추천 정책의 Owner 승인은 아직 없고, 자금 사용·운임 인식·입찰 평가의 일부 연결 규칙은 추천안을 채택하더라도 정답이 하나로 정해지지 않는다. 따라서 최종 판정은 CONDITIONAL이며, 경제 통합 및 실제 E2E 검수 준비는 BLOCKED 상태를 유지한다. 모든 개발 검토를 중단해야 한다는 의미는 아니다. 개발 소관 기술 설계는 4절에서 구체적으로 결정한다.

Gate 1 Owner 결정 원문과 A/B를 확인했다. 쉬움 시철 관할, 사전 허가 입찰, 시청/정부 분리, 0 수익성 통과, 재접수 제한, 난이도별 파산·지원 및 8개 MVP 영역을 변경하지 않는다. 1차 회신의 '시청 자동 통과'는 이번에는 **확인된 비음수 범위**로 읽는다. 음수 사업성 처리는 원문상 미확정이므로 자동 승인 또는 거부로 확대하지 않는다.

G2-Q01~08 추천안, 문서의 계산 예시, 이 보고서의 정책 권고는 Owner 승인 전 게임 규칙이 아니다. 원격 병합은 문서 게시 사실이며 Gate 2 규칙 승인 증거가 아니다.

### F-01 — 자금 예약의 갱신과 운영비 부족 정책 (BLOCKER)

- 위치: [C §5-5 L219~233](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L219), §5-9 L287, AC-09/10.
- 반영 평가: 계약 1회 지급·기성·제한잔액 유지·초과비 충당의 추천은 검산 가능할 정도로 발전했다. 예시의 C=127/R=20/F=107, 손익 27은 맞다.
- 문제 1: K는 정의만 있고 회사부담 기성 지출 시 감소식이 없다. K를 그대로 두면 이미 지출된 부담을 A에서 계속 차감한다. 자신의 예약자금 집행도 신규 약정 A로 검사하면 정상 시공이 멈출 수 있다.
- 개발 답변: TD-03의 사업별 Kᵢ, 집행 시 K 감소, 지급/기성의 원자적 갱신으로 정리한다. 이는 추천 장부의 정의를 완결하는 기술 처리이며 새 잔액 사용 정책이 아니다.
- 문제 2: R을 다른 용도로 쓰지 않는 원칙과 '음수 운영비 허용 미정'의 관계가 남아 있다. C=20, R=20, F=0에서 운영비 3을 단순 C 차감하면 C=17/R=20/F=-3이다. 차입·미지급 표현 없이 실행하면 실재 현금이 제한잔액보다 적어지며 전용 금지 검증을 통과했다고 할 수 없다. 이는 미정 분기를 택했을 때의 반례이며 문서가 이미 전용을 허용했다는 주장은 아니다.
- 결정 요청: 운영비가 자유현금 F를 초과할 때 (a) 지급 보류·미지급 또는 서비스 제한, (b) 명시적 신용/음수 장부를 도입하는 안 중 선택하고 비용 인식·운행·회복 조건을 함께 정한다. F≥비용이나 A<비용인 경우 회사부담 예약 K를 운영비가 침식할 수 있는지도 분리 결정한다.
- 개발 권고: 제한자금만 남았을 때의 단순 C 차감은 채택하지 않는다. 신용을 추가하면 부채/한도/정산 범위가 증가하고, 지급 보류안도 서비스 처리 규칙이 필요하다. 개발이 임의로 회사 파산 기준을 F 또는 A로 바꾸지 않는다.
- 종료 증거: G2-Q06/07 결정 및 두 사업·예약 감소·제한잔액만 존재·F/K 경계·총현금 음수 사례의 장부 기대값. 영향: 두 VP, 재무 UI, 공정 중단·재개, 다음 사업.

### F-02 — 완료 통행 과금과 탑승 예시 사이의 시간 계약 (HIGH)

- 위치: [C §5-7 L264~272](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L264), §5-6 L252, AC-08.
- 문제: '1회 완료 통행에 1회 과금'인데 예시는 탑승 8명을 곧바로 수익 8,000으로 계산한다. 모두 구간 안에 도착했다고 가정하면 맞지만 그 가정·이동 중 인원·완료 시각이 없다. 영업 종료 1분 전 승차, 이동시간 10분 또는 자정 통과 시 어느 날짜의 수익인지 정답이 정해지지 않는다.
- 개선: 예시에 8명 전원이 도착 완료했다는 조건을 추가하고, 요청/탑승/이동 중/완료 통행/매출을 구분한다. 집계 OD 묶음의 도착 사건으로 처리하면 개별 시민 전체 시뮬레이션 없이 구현 가능하다.
- Planning/Owner 선택: 영업 종료 시 새 탑승만 종료하고 이미 탑승한 승객은 도착·완료 과금까지 처리하는 안을 권고한다. 대안인 탑승 즉시 과금은 완료통행 규칙 변경이므로 별도 승인 필요. 만족도·이용 지표의 귀속 날짜도 함께 정한다.
- 종료 증거: 종료 직전·자정 횡단·운행 0분·도착 전 보고·완료 후 보고의 숫자 fixture. 영향: 승객 집계·일일 보고·연출·시간 시스템, 두 VP의 첫 실적 보고.

### F-05 — OD 배분·수송량·소수 이월의 시간분할 정답 (HIGH)

- 위치: [C §5-7 L260~268](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L260), [AC-08 L304](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L304).
- 문제: 접근비율이 출발·도착 중 무엇에 적용되는지, 같은 동 여러 역의 배분, U의 시간 단위·구간별 공유, 미탑승 소멸/대기 및 소수 이월의 범위가 미정이다. 예시 요청 10/U=8을 절반으로 나눌 때 각 호출마다 U=8을 주면 5+5=10명, 한 번 처리하면 8명으로 달라진다. 이 구현은 AC-08을 위반하므로 호출 횟수와 U를 연결하면 안 된다.
- 개발 결정: 외부 시간 진행 호출을 고정 시뮬레이션 경계·사건 경계에 투영하고 잔여 시간·소수 수요를 보존한다(TD-02). 렌더링 갱신 빈도가 경제 계산을 바꾸지 않게 한다.
- Planning 입력: D/w/a/q/h/U의 단위·유효 범위·정규화, 수송량이 전체 노선인지 구간별인지, 미탑승의 대기/소멸, 소수 이월의 일자 경계 정책을 명시한다. 만족도 α/β/γ 외에 수송충족·미탑승·지연률의 분모와 지연 정의도 필요하다. 배분·평가 값은 개발이 임의 확정하지 않는다.
- 종료 증거: 하나의 승인된 OD·시간대 데이터셋에 0수요, 여러 역 접근, 용량 부족, 부분일, 시간분할, 자정 이월 기대값. 영향: F-CITY/OPS/FIN, 순서 효과 검증, 운영 예측·실적 설명.

### F-06 — 계약 대기 명령과 자정 사건의 순서 (MEDIUM)

- 위치: [C §5-6 L237~248](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L237), §5-5 L219.
- 문제: 자정 처리표는 기성·완공·시험·개통을 정렬하지만, 일시정지 중 요청해 재개 후 실행하는 계약·정부 지급·공정 재개 명령의 삽입 위치가 없다. 같은 시각 지급과 기성의 선후에 따라 부족 판정과 공정이 달라질 수 있다.
- 개선: 승인된 사건 귀속 정책 아래 명령 접수/효력 시각을 구별하고, 대기 계약/지급의 우선순위 및 같은 프레임에 생성된 후속 사건 처리까지 표에 추가한다. 자정 신규 거래를 새 날짜로 귀속하는 추천과 정합하도록 새 날짜 전환 뒤 계약·지급, 이어 기성 평가를 권고한다. 돈의 사용 가능 시점이 바뀌므로 이 순서를 게임 규칙으로 확정하는 것은 Planning/Owner다.
- 개발 결정: 동시각 순서가 확정되면 정렬 키와 중복 실행 방지는 TD-02/04로 처리. 종료 증거: 자정 지급+기성, 정지 중 중복 계약, 같은 시각 재개·완공의 기대 상태/원장. 영향: 시간·재무 경계 테스트.

### F-07 — 평가·시험·초기 경제 입력의 최소 고정본 (HIGH)

- 위치: [C §5-4 L200~204](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L200), §5-6 L250~254, D §3~5.
- 문제: 모델 명칭은 구체화됐으나 확률표/지표 결합, 직접 적합 사업비 산식, r·설득, 시공 비용/기간, 시험 결함·복구·재시험 시간/비용, 초기 자금 등이 승인 데이터로 없다. fixture로 강제 결과만 보이면 정상 E2E 구현 증거가 되지 않는다.
- 개선: 정식 밸런스 전체를 기다리지 말고 'MVP 검수용 규칙·데이터 v1'을 Planning이 제출하고 Owner가 해당 용도로 승인한다. 쉬움 시철의 필요한 행만 구현 데이터로 제공하고 다른 모드 전체 구현을 추가하지 않는다. 승인된 확률 판정은 정상 엔진과 고정 시드를 사용하며 강제 분기 fixture는 단위 검증으로 분리한다.
- 종료 증거: 두 VP 초기 상태·실제 명령 순서·심사/계약/공정/완료통행/장부 기대 결과 및 실패 분기 데이터. 영향: 두 VP의 실플레이 완료, 공수 확정. 예시 금액이나 확률을 임의로 제품 규칙으로 채택하지 않음.

### F-08 — 범위·성능·세션 결정과 견적 (MEDIUM)

- 위치: [C §5-8~5-9 L276~289](https://github.com/wisberry2022/MetroManager/blob/e18b047848108383acdcef47250ee81393df2058/docs/planning/PLN-001-C.md#L276), D §4~5, G2-Q01~03·07~08.
- 문제: 최소 표현이 집계 선택형에서 열차 이동·정차·승하차 포함 추천으로 강화됐다. 대상 PC·해상도·표시 상한·목표 성능·세션 길이는 아직 없다. 저장 SHOULD 및 반복 재현만으로 외부 세션 중단 요구를 만족한다고 할 수 없다.
- 개발 답변: TD-05/06의 반복 검증 및 측정 절차는 확정한다. 현재 단계에서 성능 보장이나 디자이너 작업일 합산 견적은 내지 않는다.
- 결정 요청: Owner/HQ는 쉬움 시철·콘텐츠 상한·세션 중단/재개 요구·지원 PC 기준을 정하고 Design은 화면/연출 데이터 계약과 동시 표시 상한을 제공한다. 목표 성능은 해당 조건의 시제품 측정과 함께 검수 기준으로 승인한다.
- 영향: 저장 승격 시 복원·사건 중복·규칙 버전·호환 검증 M~L 추가, 기본 UI/연출 통합 증가. 종료 증거: 범위 선택 기록과 대상 환경·측정 장면·합격 기준.

## 5. 1차 이후 규모·선행 의존성 변화

M/L은 상대적인 구현·검증 범위이며 인일·완료일이 아니다. 1차 전체 틀은 유지되지만 아래 내용이 구체화되어 비용 상승 위험이 드러났다. 권고안을 채택한다는 조건의 비교이며 정책 승인 전 확정 견적이 아니다.

| 작업 단위 | 1차 → 2차 | 늘거나 구체화된 작업·의존성 |
| --- | --- | --- |
| 규칙·검수 데이터 | M → M, 내용 증가 | 추천 정책에서 실제 숫자·경계 정답·Owner 선택 기록으로 고정 필요. F-01~07 |
| 행정/회사/역 | M → M | 부모 유형·외부시 fixture로 불확실성 감소. 콘텐츠 좌표·연결성 입력 필요 |
| 시간/원장 | L → L, 검증량 증가 | K 예약, 다중 제한계정, 자정 명령 순서, 부분일·시간분할·중복 사건 |
| 두 사업 경로 | L → L, 동일 사업 모델에 따라 상방 위험 | 공개 평가·확률표, identity/revision, 신규 사실 이력. 유사도 일반화는 슬롯안보다 큼 |
| 시공/검증 | L → L, 상태·회귀 범위 증가 | 자금 중단·재개, 빠름/느림 선택, 두 검증 절차·무효화·재시험 |

핵심 경로: Owner 정책 선택 → Planning 검수용 데이터/정답 → 행정·회사 무결성 → 공통 시간·원장 → 취득 경로 → 시공·검증 → OD 운영·정산 → 실제 UI 및 두 VP 검수. UI 데이터 계약·표현 설계는 정책 선택과 병행 검토 가능하나 기획팀이나 개발팀이 Design의 배치·에셋 수량을 대신 확정하지 않는다.

D의 15~25 디자이너 작업일과 개발 M/L을 합산하지 않는다. 수량 확정·F-01~07 해소·기술 시제품 후 개발 작업 단위를 다시 견적하고 HQ가 인력·일정으로 통합한다.
