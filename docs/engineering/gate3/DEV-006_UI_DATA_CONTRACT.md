## 1. 공통 봉투와 명령

모든 값은 권위 시뮬레이션 상태에서 공급한다. UI는 운임·비용·판정·자격을 다시 계산하지 않는다. 필드명은 초안이며 공급 타입·경로는 실행 티켓에서 합의한다.

| 제안 필드 | 타입·단위·의미 | 검수/소비 규칙 |
| --- | --- | --- |
| rules_version/data_version | 문자열 및 데이터 식별값 | 같은 계약 revision의 값만 비교. 다른 버전 재사용 금지 |
| snapshot_revision | 단조 증가 정수 | 서로 다른 revision의 현금/원인/버튼 상태를 섞지 않음 |
| simulation_minute/day_id | 정수 게임분 / 파생 일자 식별자 | 벽시계·프레임 시각 아님. 날짜/분 값의 실제 인코딩은 DEV가 일관 정의 |
| observation_phase | 안정된 T 처리 완료 상태 또는 과거 보고 | 자정/기성/도착/정산 중간값을 완결 상태처럼 화면에 혼합하지 않음 |
| entity_id/plan_revision | 안정 ID / 정수 | 행정·역·노선·사업·계획·공고·심사 회차를 구별, UI 이름으로 동일성 결정 금지 |
| available/value | 논리값 / 의미 타입 | 미수신/미계산은 자료 없음, 실제0은 숫자0. 오류는 별도 reason으로 제공 |
| period_start/period_end | 반열린 게임 시각 구간 | 예상 하루와 부분일 실적을 동일 기간처럼 비교하지 않음 |
| reason_codes/allowed_actions | 의미 코드 목록 / action과 허용값·사유 | 상태와 원인 분리. 구체 한국어 문구/강조는 Design이 정함 |

명령은 command_id, 대상ID/계획revision, requested_at, expected_snapshot_revision, payload를 가지며 결과에 accepted/rejected/pending, effective_at, reason, result_revision을 돌려준다. 화면의 허용 표시는 안내이고 실제 처리는 효력 시각의 규칙을 다시 검사한다. 중복 command_id는 경제/난수/횟수 효과를 반복하지 않는다. 명령 판정은 효력 단계에서 현재 자격/자금을 재검사한다. 봉투 revision만 바뀌었다고 일괄 거부하지 않으며, 확인한 계획revision·회차·계약조건이 바뀌면 STATE_CHANGED 등 사유와 갱신/재확인을 공급한다. 바뀐 금액/계획으로 대체 실행하거나 자동 재접수하지 않는다. 같은 명령을 무조건 다음날 재실행하는 등 새 게임 규칙을 추가하지 않는다.

일시정지 중 조회/계획 편집은 허용하고 시각 의존 효과는 동결한다. 계약·심사 대기 명령의 업무시간·재개 효력은 승인 순서대로 판정한다. 제품에 없는 직접 취소·정산 토글은 allowed_actions에도 노출하지 않는다.

## 4. 합의·검증 종료 조건

DEV는 필드/단위·기간·처리 경계·오류/허용행동 공급 책임을 진다. Design은 화면별 소비·라벨/계층·지도/목록 조작과 상태 매핑을 검토한다. Planning은 용어·계산 규칙의 진위를 확인한다. HQ는 교차 의존성 및 미결 상태를 추적한다.

P05/P06/P07/다음사업 통합 티켓 확정 전 같은 계약 revision에 대해 (1) 공급/화면 매핑표, (2) 위 사례의 초기/기대/실제 값, (3) 틱/날짜 변경 시 혼합 snapshot 없음, (4) 중복·stale 입력 거부, (5) 현재/과거·예상/실적·없음/0 구별을 대조하고 PR head와 수용 의견을 남긴다. UI-DC-01~07은 아래 고정 Design 원문과 정적 공급·소비 의미를 대조했다. 실제 값/화면 조작·Godot fixture와 공동 구현 인수는 별도이며 정적 수용으로 대체하지 않는다.

가독성·해상도·최대 표시량·폰트·FPS 목표는 별도 G3-02/03의 Design/DEV 제안과 Owner 선택 대상이다. 기존 1280×720/40px 제안값을 승인 규격으로 채택하지 않는다. 계약 차이로 정책 변경이 필요해지면 해당 ID/AC·이유·대안의 RFC로 올린다.

## 5. 계약 효력·현재 안내·동일 T 신규 탑승

승인 SEM-03 순서는 [이전,T) 비용/공정 → 자정 보고 고정·새날 → T 계약/정부지급 → 기성/완공 → 시험/개통 → T 도착운임 → B 우선정산 → T 신규탑승 판정이다. 계약 자금 검사는 계약 단계에 이미 존재하는 자금/의무로 수행한다. 같은 T 후순위 도착운임을 앞선 계약에 사용하지 않는다. A=max(0,F−ΣK)는 그대로며, 미지급 우선의무와 추가약정 가능성은 별도 결과로 설명한다.

명령 결과는 command_id/effective_at/decision_phase/decision_snapshot_revision/result_revision/reason에 연결한다. 현재 패널은 최신 snapshot의 allowed_actions를 사용한다. 늦은 거부 결과는 당시 명령 기록만 갱신하고 현재 버튼 상태를 덮지 않는다. 동일 command_id는 기존 결과만 반환하며 경제/난수/회차 효과를 복제하지 않는다. 새 시도는 현재 상태를 확인한 사용자의 명시적 새 입력이다.

READY이고 현재입력과 일치할 때만 현재 예측으로 소비한다. 현재 유효한 결과가 없는 계산중/실패는 자료없음+상태/사유다. 이전 입력 결과는 이전 결과/버전/기간을 명시한 비교용이며 제출판정에 사용하지 않는다. 같은 입력의 재조회는 시간/난수/불필요한 계산을 진행시키지 않는다. 동기 계산이면 READY/FAILED로 직접 종료 가능하며 로딩연출을 위한 대기시간을 만들지 않는다.

cohort 합계와 현재 이동중은 일치해야 한다. 최신 일정 revision을 제공하고 예정도착과 실제완료를 구별하되 정시보장·오차 숫자를 새로 약속하지 않는다. UI 로컬 관측시각은 게임시간·운임·정산 입력으로 역사용하지 않는다.

## 8. 도형·제품 목표·수용 상태

행정 부모·역 소속·허용 간선이 판정 원본이다. 표시 도형의 point-in-polygon으로 이를 재분류하지 않는다. Design이 선택한 추상4×3 시안·동일 안정ID의 목록/지도 조작은 공급 원칙과 연결 가능하다. 도형의 형태·픽셀규격은 Design 소관이며, Planning이 미제공 경계 도형을 새로 확정해야 한다는 차단 조건은 없다. 실제 목업/클릭·밀집·목록 동등성은 상세 에셋 확정 전 검증한다.

UI-DC-08은 이번 UI-DC-01~07 정적 의미 수용 범위에서 제외한다. 기존 집계+열차이동/정차+승하차 아이콘은 유지하고 PC/뷰포트/폰트/FPS·연출 상한은 G3-03 별도 제안·Owner 선택 대상이다. 값 미정이 이번 분석 문서 제출을 차단하지 않는다.

[Design PR #30 고정 head의 결정서 §9](https://github.com/wisberry2022/MetroManager/blob/47fe5923c8ff730dbbf6c03daace304e96a856bc/docs/design/tasks/DSG-002_UI_PRESENTATION_DECISIONS.md#9-dev-회신-대조디자인-수용-기록-2026-11-01-v02)에 DESIGN_SEMANTIC_ACCEPTED와 추가 질문 없음이 기록됐다. 이는 고정 head의 정적 의미 수용 증거이며, 제출 직전 main 8ef97626ba96844648a6de2e2cb9654e6816ce40의 #30 병합도 확인했다. Planning 후속 ACCEPT는 확인하지 못했으며 대신 완료 처리하지 않는다. 새로운 정책 질문·HQ L3 상정 필요는 발견하지 않았다. 실제 공급/게임 AC·VP/화면·목업·사용성/성능은 NOT_RUN, 공동 구현 인수와 Owner 승인/DONE은 별도다.
